# 发布工作流

> 适用仓库：`xiaotu-inventory`（小兔进销存）、`dev_card_cpp`（DevCard）、`mote`（Mote）
> 配套文档：[OSS-发布布局](./OSS-发布布局.md)（每个对象键、大小、缓存头）

## 1. 总体结构

```
构建机（本地 / GitHub Actions）
   │  产出安装包 + 更新清单
   ▼
OSS 桶 xiaotu-update（cn-hongkong）→ 自定义域名 dl.xiaotu.online（CNAME 直连 OSS，无 CDN 层）
   │  安装包（immutable 1 年）+ 清单（60s）
   ▼
客户端启动 / 下载页 site.js 读取清单
```

三个产品共用同一套目录与缓存规则，只有「谁构建、谁上传」不同。

> `dl.xiaotu.online` 通过 OSS 的 CNAME 域名（`xiaotu-update.cn-hongkong.thepacificxxs.com`）
> 直接指向桶，**没有 CDN 层**：上传后源站立即生效，无需刷新缓存。响应里的
> `Cache-Control` 由 OSS 原样返回，只影响客户端侧缓存（清单 60s、安装包 1 年）。

## 2. 通用规则

| 项 | 约定 |
|---|---|
| 桶 / 区域 | `xiaotu-update` / `cn-hongkong` |
| 域名 | `https://dl.xiaotu.online` |
| 安装包 | `<product>/<v2 文件名>`（`<product>-<version>-<os>-<arch>-<type>.<ext>`），`public, max-age=31536000, immutable` |
| 更新清单 | `<product>/updates/<channel>/manifest.json`、`appcast.xml`，`no-cache, max-age=60`（v1 清单已退役删除，见 5 节） |
| 发布说明 | `<product>/release-notes-<版本>.html` |
| 手册 | `<product>/manual.pdf`（固定名，手工上传） |
| 版本 | **必须递增**（macOS 的唯一更新判据）；安装包同名覆盖无效，改包必须升版本（唯一例外：修复清单错误而同版本重发，见 4.1） |
| 构建号 | **由 `tools/release/gen_build.py` 自动生成**（`YYYY * 10^12 + git rev-list --count`，16 位），不再手填时间戳。同一 commit 跨机器、跨平台一致，macOS 与 Windows 必须同号；`guard.py preflight` 会校验清单 `build` == 编译注入值，并校验同版本两平台 build 同源。CMake 注入：小兔 `XIAOTU_BUILD` / Mote `MOTE_BUILD` / DevCard `DEVCARD_BUILD_STAMP`，客户端同版本时靠它判新（macOS 客户端仍按 `version` 判定，`build` 不参与） |
| 通道 | `stable`（默认）/ `beta` |
| 凭据 | 按产品不同，见 2.1 |

### 2.1 凭据与签名私钥位置

| 产品 | OSS 凭据 | 更新签名私钥 |
|---|---|---|
| 小兔 | `~/.config/xiaotu-updates/.env`（AK/SK/桶名/区域，600；Windows 脚本兼容 `oss-credentials.env`） | `~/.config/xiaotu-updates/update_signing_2026.pem` |
| DevCard | `~/.config/devcard/release.env` | Sparkle（appcast）：`~/.config/devcard/sparkle-keys/private_key.pem`；清单 v2：`~/.config/devcard/manifest-keys/ed25519_seed.b64` |
| Mote | `~/.config/xiaotu-updates/.env`（可用 `OSS_ENV_FILE` 覆盖） | 清单：`~/.config/mote-updates/ed25519_seed.b64`（`SIGN_KEY`）；Sparkle：`~/.config/mote-updates/sparkle_ed25519_seed.b64`（`SPARKLE_KEY`）。两把独立密钥，不得混用 |

私钥只在 Mac 上；Windows 构建机通过 GitHub Secrets 接收签名材料（仅清单签名用）：
小兔 `XIAOTU_UPDATE_SIGNING_KEY`（Ed25519 私钥 PEM）、DevCard `DEVCARD_UPDATE_SIGNING_KEY`、
Mote `MOTE_UPDATE_SIGNING_KEY`（32 字节种子 base64）。

### 2.2 发布门禁 guard.py 与清单生成器 manifest_v2.py

三个仓库各有一份 `tools/release/guard.py` 和 `tools/release/manifest_v2.py`，内容完全一致
（CI 用同名 `.sha256` 校验，单仓库私改会失败）。

| 阶段 | 检查内容 |
|---|---|
| `preflight`（上传前） | 产品/通道合法、文件命名（**仅 v2 规则**，v1 已于 2026-11-18 全量删除）、版本单调、同名覆盖风险、dmg 内 `SUFeedURL`/版本/公钥、绿色包内清单地址；manifest.json 结构与 Ed25519 签名；**Windows BUILD_STR**：三产品同口径（Mote 搜 `MOTE_BUILD=`、小兔搜 `XIAOTU_BUILD=`、DevCard 搜 `DEVCARD_BUILD_STAMP=`），绿色包 zip 扫静态字符串与 `--build` 参数比对，setup.exe 单独出现时用 innounp 解包后扫；zip+setup 共存时只扫 zip（同源于绿色包）；**跨平台 build 同源**：同版本两平台 build 必须相同，不一致直接阻断（单平台热修用 `--allow-build-drift` 显式放行并记录原因）；**DevCard 专属**：清单 `platforms.macos` + `platforms.windows` 必须同时存在 |
| `verify-live`（上传后） | 清单字段、大小、SHA256、下载 URL、Content-Type、appcast 版本、`edSignature` |
| `selftest` | 50 项离线用例（含 v2 schema 与 Ed25519 固定向量、DevCard 双平台强校验、跨平台 build 同源校验、三产品 BUILD_STR 正向匹配 + build 不一致阻断 + 缺 stamp warn 跳过），CI 每次运行 |
| `manifest_v2.py selftest` | 26 项离线用例（RFC 8032 向量、generate→verify 全流程、`--build` 两平台都必须 > 0） |

v2 清单（`manifest.json`，schema 与命名见[更新清单Schema-v2](./更新清单Schema-v2.md)）
已上线，生成器与门禁用法：

```bash
# 生成并签名（--prev 合并另一平台段后整体重签）
tools/release/manifest_v2.py generate --product mote --platform windows \
    --version 1.0.6 --build 202611191435 --artifact portable=x.zip --key <私钥> \
    --prev dist/manifest.json --out dist/manifest.json
# 门禁：v2 命名 + 签名 + 与产物一致性（--schema v2 参数已于 2026-11-19 移除，强制 v2）
tools/release/guard.py preflight --product mote --kind win --file x.exe \
    --build 202611191435 --manifest dist/manifest.json --pub <公钥> --offline
```

修改任一文件后必须同步：

```bash
tools/release/sync_guard.sh                  # 在 mote 仓库执行，同步两份并重写 .sha256
tools/release/sync_guard.sh --check-build-str  # 额外：三仓库 BUILD_STR 合规检查
```

> `--check-build-str`（2026-11-20 起覆盖 DevCard）逐仓库验证三点：
> 1) CMake 侧有构建号注入（Mote/小兔顶层 CMakeLists.txt 直接宏、DevCard `cmake/devcard_version.cmake` 的 `devcard_add_build_stamp()` 函数）；
> 2) 壳源码有 `kBuildStamp[]` 静态字符串；
> 3) guard.py `_BUILD_STAMP_PREFIX` 映射正确。
> 三产品同口径，不再跳过 DevCard。

#### `doctor`：发布前预检（2026-11-19 新增）

一条命令跑通完整发布链路的**环境自检**，不改动仓库，只读检查：

```bash
python3 tools/release/guard.py doctor --product mote --platform both
# 输出： 签名密钥 / OSS 凭据 / oss2 环境 / Sparkle sign_update / cmake / git / spctl / codesign
#       / hdiutil / xcrun 等 10+ 项，逐项 ✓/!/✗ 汇总
```

三产品默认密钥路径已内置：
- mote：`~/.config/mote-updates/ed25519_seed.b64` + `sparkle_ed25519_seed.b64`
- xiaotu：`~/.config/xiaotu-updates/update_signing_2026.pem`

- OSS 凭据三产品共用 `~/.config/xiaotu-updates/.env`（DevCard 可用 `OSS_ENV_FILE` 覆盖）

## 3. macOS 发布

一条命令完成：构建 → 签名 → 公证 → 校验包内 feed 地址 → 生成 `appcast.xml` / `manifest.json`（v2）→ 上传 → 线上复核。

**发布前有三层门禁（2026-11-19 起）：**

| 层 | 位置 | 行为 |
|---|---|---|
| configure 层 | CMakeLists.txt `-DMOTE_STRICT_BUILD=ON` | Sparkle.framework 缺失 → **FATAL_ERROR** |
| configure 自动修复 | CMakeLists.txt（macOS 分支） | Sparkle tarball 缺 `Versions/Current` 符号链接 → 自动探测并 `CreateLink Current -> <letter>` |
| 打包脚本层 | `package_macos.sh` | `.app/Contents/Frameworks/Sparkle.framework` 必须存在 + `.app ≥ 1024 KB` → exit 1 |
| 发布脚本层 | `publish_macos.sh` | DMG 内同样双保险（挂载后再次校验） |

> Sparkle 2.x tarball（`Sparkle-2.7.0.tar.xz`）已知缺陷：顶层 `Sparkle -> Versions/Current/Sparkle`
> 符号链接存在，但 `Versions/Current` 本身缺失。configure 阶段会自动探测 `Versions/` 下
> 唯一子目录（如 `B`）并补建 `Current -> B`，无需手动 `ln -sfn B Current`。
> 新机器 setup 不用再跑这个命令——CMake 自动处理。
>
> 开发机本地开发如果没有 Sparkle，可以不加 `-DMOTE_STRICT_BUILD=ON`，configure 只会 WARNING
> 并继续；产物缺 framework 时应用内更新会退回浏览器下载。

Mote 的构建入口只有 `native/CMakeLists.txt`（AppKit + WKWebView，无 Qt）；
本地产物是 `dist/Mote-macOS-native-<版本>.zip` / `.dmg`，发布脚本上传时按 v2 规则
改名为 `mote-<版本>-macos-arm64.dmg`。

| 产品 | 版本来源 | 命令 |
|---|---|---|
| Mote | `VERSION.txt` | `tools/release/publish_macos.sh` |
| DevCard | `VERSION.txt` | `tools/release/publish_macos.sh` |
| 小兔 | `VERSION.txt` | `tools/package/publish_oss.sh` |

> 构建号不再手工指定：三个 macOS 发布脚本都调 `tools/release/gen_build.py` 取号，
> 并把同一个值同时写进 `CFBundleVersion` 与 v2 清单 `platforms.macos.build`
> （显式传 `DEVCARD_BUILD` / `XIAOTU_BUILD` / `BUILD` 时以传入值为准）。
> macOS 客户端的「是否有更新 / 待安装 / 验证期 / 恢复模式」仍按 `version` 判定，
> `build` 只用于 Sparkle appcast 比较、灰度分桶与诊断。

可选参数（三个产品接口不同）：

Mote 用环境变量开关：

```bash
bash packaging/package_macos.sh --dmg                     # 出 dist/Mote-macOS-native-1.0.4.dmg
SKIP_UPLOAD=true tools/release/publish_macos.sh           # 只本地生成清单，不碰 OSS
DMG_PATH=dist/Mote-macOS-native-1.0.4.dmg tools/release/publish_macos.sh  # 复用已有 dmg
```

DevCard 用命令行参数：

```bash
tools/release/publish_macos.sh --skip-build     # 复用已有 dmg
tools/release/publish_macos.sh --notes "说明"   # 写入 appcast 发布说明
tools/release/publish_macos.sh --dry-run        # 只出包与清单，不上传
```

小兔用环境变量开关：

```bash
OSS_SKIP=true tools/package/publish_oss.sh      # 只本地生成 + 验签，不碰 OSS
WARMUP=false tools/package/publish_oss.sh       # 关闭发布后的下载可达性验证
PRODUCT=xiaotu tools/package/publish_oss.sh     # 产品目录，默认且仅接受 xiaotu
```

## 4. Windows 发布

### 4.1 DevCard / Mote：走 GitHub Actions

1. 升版本并提交推送（只改仓库根 `VERSION.txt`）
2. Actions →「Windows 发布」→ Run workflow
   - 勾 `dry_run`：只构建、出包、跑门禁，不上传
   - 勾 `skip_setup`：只发绿色包，跳过 Inno 安装包
   - 都不勾：正式发布（绿色包 + 安装包 + 清单）
3. 完成后按第 6 节核对

需要配置的 Secrets：`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`。

本地发布时：`packaging/package_windows_native.ps1` 出绿色包，
`packaging/build_installer.ps1` 出 `dist/Mote-Setup-<版本>.exe`；
`publish_windows.ps1` 检测到安装包就一并上传，不存在则只发绿色包。

> **构建号必须与二进制里的值一致。** 客户端在版本相同时靠 `build`
> 判断有没有新构建；如果清单的 `build` 大于安装包里编译进去的值，用户每次检测都会
> 被提示同一版本，装完照旧，形成死循环（2026-11-19 mote 1.0.4 即因此重发）。
> 三产品注入机制：
>
> | 产品 | CMake 注入 | BUILD_STR 壳源码 |
> |---|---|---|
> | Mote | `native/CMakeLists.txt` 一处直接注入：`-DMOTE_BUILD=<int>` + `-DMOTE_BUILD_STR="<int>"` | `platform/win/updater.cpp`：`kBuildStamp[] = "MOTE_BUILD=" MOTE_BUILD_STR` |
> | 小兔 | 顶层 `CMakeLists.txt` 校验 `XIAOTU_BUILD` 必填；实际注入分散在两处：`shell/win/CMakeLists.txt` 给 updater 注 `XIAOTU_BUILD=<int>` + `XIAOTU_BUILD_STR="<int>"`，`core/CMakeLists.txt` 给 core 注 `XIAOTU_BUILD=<int>` | `shell/win/updater_win.cpp`：`kBuildStamp[] = "XIAOTU_BUILD=" XIAOTU_BUILD_STR` |
> | DevCard | `cmake/devcard_version.cmake` 的 `devcard_add_build_stamp(target)` 函数同时注入 `-DDEVCARD_BUILD_STAMP=<int>` + `-DDEVCARD_BUILD_STAMP_STR="<int>"`（双宏：整数给 core 用、字符串给 shell 拼 BUILD_STR 用） | `shell/win/main.cpp`：`kBuildStamp[] = "DEVCARD_BUILD_STAMP=" DEVCARD_BUILD_STAMP_STR` |
>
> Actions 里构建与发布是两个步骤、两个进程：构建步骤把实际生效的值经
> `<PRODUCT>_BUILD_STAMP` 传给发布步骤。本地发布时 `publish_windows.ps1` 优先用 `-Build`，
> DevCard 无 SkipBuild 时脚本自动触发 re-configure 确保 CMake 重新注入。

#### DevCard Windows 构建号注入验证步骤（每次发版前必跑）

`dev_card_cpp/tools/release/verify_build_stamp.ps1`（UTF-8 + BOM，零依赖纯 PowerShell 5）一次性跑通 **编译期注入 → 运行时读取 → 二进制 grep → manifest 签名** 全链路。

**运行前提**：Windows 构建机（VS 2022 C++ 工具链），PowerShell 5。

```powershell
# 最简：自动生成 UTC 时间戳做 build number，完整 configure + build + 7 项验证
cd D:\projects\dev_card_cpp
powershell -ExecutionPolicy Bypass -File tools\release\verify_build_stamp.ps1

# 指定固定 Stamp（推荐：和将要发布的 build 号一致）
powershell -ExecutionPolicy Bypass -File tools\release\verify_build_stamp.ps1 -Stamp 202611211200

# 已有构建目录时跳过重编译（-SkipBuild），只验 T3~T7
powershell -ExecutionPolicy Bypass -File tools\release\verify_build_stamp.ps1 -SkipBuild

# 自定义构建目录
powershell -ExecutionPolicy Bypass -File tools\release\verify_build_stamp.ps1 `
    -Stamp 202611211200 -BuildDir build-win -FallbackDir build-win-fb
```

**覆盖项**（脚本逐个 PASS/FAIL 打印，FAIL 直接 ExitCode 1）：

| T | 验证内容 | 方法 | PASS 条件 |
|---|---|---|---|
| T1 | CMake configure 输出 | 扫描 configure 输出里的 "DevCard 构建号注入" 日志 | ≥ 4 行（core / server / server-exe / shell-win 四个 target 各一行） |
| T2 | CMakeCache 落盘 | 读 `CMakeCache.txt` | `DEVCARD_BUILD=<Stamp>` 精确匹配 |
| T3 | 运行时读取链路 | 执行 `devcard_core_tests.exe` | exit 0 + 测试里 `compiled_build_number()==Stamp` 断言成立 |
| T4 | shell 壳 BUILD_STR grep | 字节扫描 `shell/win/Release/DevCard.exe` | 找到 `"DEVCARD_BUILD_STAMP=<Stamp>"` 静态字符串（shell 是自动更新壳，必须有） |
| T6 | 无注入回退链路 | configure **不带** `-DDEVCARD_BUILD`、重新 build | (a) configure 输出 4 行 "DevCard 未注入构建号" 日志；(b) 回退构建的 `devcard_core_tests.exe` 通过（`compiled_build_number()==0`）；(c) 回退构建的 `devcard-server.exe` 内 **无** `DEVCARD_BUILD_STAMP=`（server 不做自动更新，不需要标记） |
| T7 | manifest 生成对齐（可选） | 用 `manifest_v2.py generate --build <Stamp>` 生成 dummy manifest | 输出 JSON 的 `platforms.windows.build == Stamp`。需要本机有签名密钥 `~/.config/devcard/manifest-keys/ed25519_seed.b64`，密钥不存在时自动 SKIP |

**2026-11-19 实测输出示例**（7/7 PASS + T7 SKIP，因为本机无签名密钥）：


**发版前 checklist**：每次 DevCard Windows 发版（GitHub Actions 或本地 `publish_windows.ps1`）之前，先在 Windows 构建机跑一次 `verify_build_stamp.ps1 -Stamp <本次发布的 build 号>`——脚本会在 T1 阶段自己 generate 一个独立的 build 目录，完全不污染仓库，跑完后自动清理。

#### Mote 构建号注入验证

Mote `native/CMakeLists.txt` 一处直接注入 `-DMOTE_BUILD=<int>` + `-DMOTE_BUILD_STR="<int>"`，壳 `platform/win/updater.cpp` 放 `kBuildStamp[] = "MOTE_BUILD=" MOTE_BUILD_STR`。注入路径稳定（不像 DevCard 有双宏、小兔有两处分散注入），**不需要专门的验证脚本**。

**GitHub Actions**（主要路径）：构建步骤自动注入、release 步骤 `guard.py preflight --build <STAMP>` 自动扫壳 `Mote.exe` 里的 BUILD_STR 二次校验——**Actions 里 BUILD_STR 验证是默认开启的**，不会遗漏。

**本地出包验证**（Actions 额度不足时）：出包后先跑 dry-run，再按需手动四验：

```powershell
cd D:\projects\mote-md

# 【路径 1 · 快速（推荐）】dry-run，完整 guard.py preflight + BUILD_STR 二次校验
powershell -ExecutionPolicy Bypass -File packaging\publish_windows.ps1 -Build 202611190958 -SkipUpload
```

dry-run PASS 就发；FAIL 时手动四验（命令结构同小兔，换这几个常量）：

| 小兔 | Mote | 说明 |
|---|---|---|
| `product = xiaotu` | `product = mote` | guard.py --product 参数 |
| `shell\win\build\xiaotu-shell.exe` | `build\windows\shell\win\Mote.exe`（或 `build\windows\Mote.exe`，看 CMake 输出） | 壳 EXE 路径 |
| `XIAOTU_BUILD=` | `MOTE_BUILD=` | 字节扫描 pattern（`[Text.Encoding]::ASCII.GetBytes("MOTE_BUILD=")`） |
| `xiaotu-<Ver>-win64-portable.zip` | `Mote-<Ver>-win64-portable.zip`（实际看打包脚本输出） | v2 重命名 |
| `xiaotu-<Ver>-win64-setup.exe` | `Mote-<Ver>-win64-setup.exe` | v2 重命名 |
| `build\package\win\xiaotu-inventory-<Ver>-win64.zip` | `dist\Mote-Windows-<Ver>.zip`（或打包脚本输出路径） | 原始 zip 路径 |

> **注意**：Mote 壳在 Windows 构建里的输出目录和 EXE 名可能随 CMake 目标名调整——**手动四验前先跑一次 build-release.cmd / package_windows_native.ps1 看实际产物**，把路径填对再跑 guard.py。dry-run 路径 1 不用关心这个，publish_windows.ps1 会自动找产物。

```powershell

#
# build-release.ps1 只验了壳内清单地址，没验 BUILD_STR。
# BUILD_STR 是客户端版本相同时判断"有没有新构建"的唯一依据——
# 编进去的值不对，用户每次检测都会被提示同一版本、装完照旧（2026-11-19 mote 1.0.4 即因此重发）。
#
# 两条验证路径，任选其一：

# 【路径 1 · 快速（推荐）】直接跑 publish_windows.ps1 -SkipUpload
#   -SkipUpload 走完整的 guard.py preflight 链路（重命名 zip 为 v2 格式 → 解包 → 扫 shell.exe
#   → grep XIAOTU_BUILD=<digits> → 与 -Build 参数比对 → 签名校验 → manifest generate），
#   全部通过才算构建号链路没问题；FAIL 直接 ExitCode 1 并打印原因。
powershell -ExecutionPolicy Bypass -File tools\package\publish_windows.ps1 `
  -Build 202611190003 -SkipUpload

# 【路径 2 · 手动四验（dry-run 失败时排错用）】逐环节定位
$Stamp = "202611190958"       # 换成本次 build 号
$Ver   = "1.0.4"              # 换成本次版本

# ① CMakeCache 落盘（文本文件，Select-String 安全）
Select-String -Path "build\windows\CMakeCache.txt" -Pattern ("^XIAOTU_BUILD=" + $Stamp + "`$")
#   输出 XIAOTU_BUILD:UNINITIALIZED=$Stamp 才算 PASS

# ② shell.exe BUILD_STR 字节 grep（必须用字节扫描——Select-String 把 .exe 当 UTF-8 文本读，

$bytes = [IO.File]::ReadAllBytes("shell\win\build\xiaotu-shell.exe")

$found = $false
for ($i = 0; $i -le $bytes.Length - $pat.Length - 20; $i++) {
  $ok = $true
  for ($j = 0; $j -lt $pat.Length; $j++) { if ($bytes[$i+$j] -ne $pat[$j]) { $ok=$false; break } }
  if ($ok) {
    $tail = [Text.Encoding]::ASCII.GetString($bytes[$i..($i+30)])
    Write-Host "shell.exe FOUND at offset $i : $tail"; $found = $true
  }
}
if (-not $found) { Write-Host "FAIL shell.exe 内没有 XIAOTU_BUILD= 字符串"; exit 1 }

# ③ 绿色包 zip 内 shell.exe grep（zip 是最终发布物，必须也有 BUILD_STR）
#    方式 a（推荐）：直接跑 guard.py preflight（需要 zip 是 v2 命名）
$tmpDir = "$env:TEMP\guard-v2-test-xiaotu"
New-Item -ItemType Directory -Force -Path $tmpDir | Out-Null
Copy-Item "build\package\win\xiaotu-inventory-$Ver-win64.zip" `
          "$tmpDir\xiaotu-$Ver-win64-portable.zip"
Copy-Item "packaging\win\out\xiaotu-inventory-$Ver-win64-setup.exe" `
          "$tmpDir\xiaotu-$Ver-win64-setup.exe"

python tools\release\guard.py preflight --product xiaotu --kind win `
  --file "$tmpDir\xiaotu-$Ver-win64-portable.zip" --build $Stamp --offline

# ④ guard.py preflight 对 zip + setup 双产物
python tools\release\guard.py preflight --product xiaotu --kind win `
  --file "$tmpDir\xiaotu-$Ver-win64-setup.exe" `
  --build $Stamp --zip "$tmpDir\xiaotu-$Ver-win64-portable.zip" --offline
#   setup + zip 同时存在时 guard.py 只扫 zip（同源于绿色包），
#   输出 "✓ setup.exe 同源于已校验的绿色包，跳过 build stamp 扫描" 才算 PASS

Remove-Item -Recurse -Force $tmpDir -ErrorAction SilentlyContinue
```

`publish_windows.ps1` 自动：
1. 读仓库根 `VERSION` 拿版本号

3. 找签名私钥（`-SignKeyPath` 显式传入 → `~/.config/xiaotu-updates/update_signing_2026.pem` → CI 环境变量 `XIAOTU_UPDATE_SIGNING_KEY`）

5. 调 guard.py `preflight`（v2 命名 + Ed25519 签名 + 绿色包内嵌地址 + **BUILD_STR 二进制二次校验**）
6. 凭据轮换自检（AccessKey 命中 git 受版本控制的文件即拒绝）
7. OSS 上传 → 线上 reachability 校验 → guard.py `verify-live`

> **BUILD_STR 机制**：2026-11-19 上线，CMake 加 `-DXIAOTU_BUILD_STR=<UTC>` 字符串宏，

> setup.exe 单独存在时 guard.py 用 **innounp** 解包 ISCC 安装包后再扫。

### 4.3 三产品 Windows 构建号注入验证速查

每次发版前按产品类型选对应路径，**不是三产品都要跑**：

| 产品 | 推荐验证 | 注入复杂度 | 覆盖链路 |
|---|---|---|---|
| **DevCard** | `verify_build_stamp.ps1 -Stamp <N>`（7 项，含双宏、回退链路、运行时断言） | 高：双宏 + 函数注入 + 无注入兜底 | CMake 输出 → CMakeCache → devcard_core_tests 断言 → shell.exe BUILD_STR → 回退构建 |
| **小兔** | `publish_windows.ps1 -SkipUpload -Build N`（一条命令）；dry-run FAIL 时手动四验 | 中：顶层校验 + shell/win + core 两处分散注入 | CMakeCache → shell.exe BUILD_STR 字节 grep → zip preflight → zip+setup preflight |
| **Mote** | Actions 自动开；本地同小兔（dry-run 或手动四验，换 `MOTE_BUILD=` pattern） | 低：`native/CMakeLists.txt` 一处注入 | 同小兔 |

**为什么 DevCard 需要专门脚本**：双宏注入（`DEVCARD_BUILD_STAMP` 整数给 core + `DEVCARD_BUILD_STAMP_STR` 字符串给 shell）如果只配了一半，构建照常通过但运行时 `compiled_build_number()` 行为诡异。T6 显式验证无注入兜底链路就是为了拦截这种半配状态。小兔/Mote 没有双宏，一条路径不可能半配，所以 dry-run 的 guard.py preflight 足够。

## 7. 常见拒绝原因

| 报错 | 原因 / 处理 |
|---|---|
| `版本回退` | 没升版本，或版本小于线上 |
| `目标已存在且大小不同` | 同版本重发，安装包不可覆盖，升版本 |
| `dmg 内 SUFeedURL 与发布地址不一致` | 产物是旧构建，重新构建，不要 `--skip-build` |
| `绿色包内嵌地址不是 .../updates/.../manifest.json` | 壳用了旧源码，重建壳 |
| `缺少 OSS_ACCESS_KEY_ID` | 凭据文件缺失或权限不是 600 |
| `清单 404` | 上传失败，或客户端/浏览器缓存了旧的 404（清单 60s 内可能仍命中缓存），稍后重试 |
| 客户端反复提示同一版本 | 清单 `build` 大于安装包内 `MOTE_BUILD` / `XIAOTU_BUILD` / `DEVCARD_BUILD`：重发同版本修复，或升版本发布；发布后按第 6 节第 5 项核对。三产品同口径（2026-11-19 起 DevCard 也适用） |
| `DevCard v2 清单 platforms 缺少 ['macos'/'windows']` | DevCard 当前阶段两平台同时发布，v2 manifest.json 必须同时含 `platforms.macos` + `platforms.windows`；发布脚本应从线上清单 `--prev` 合并后整体重签 |
| `未能确定编译时的 MOTE_BUILD` | `build-native-ninja/CMakeCache.txt` 里没有该变量（构建时未传 `-DMOTE_BUILD`），用 `-Build` 显式传入编译值 |

### 9.1 给已发布版本补发 / 更换说明页

发布时漏了说明页（或要换成新的地址），不需要重新打包，按下面四步即可：

```bash

set -a; . ~/.config/xiaotu-updates/.env; set +a
~/.venv-oss/bin/python - <<'PY'

with open("docs/release-notes-1.0.4.html", "rb") as f:
    bkt.put_object("mote/release-notes-1.0.4.html", f,

PY

# ② 取线上清单
curl -fsSL https://dl.xiaotu.online/mote/updates/stable/manifest.json -o dist/manifest-live.json

# ③ 只改 notes_url 并整体重签（其余字段与签名前的结构原样保留）
python3 tools/release/manifest_v2.py resign --manifest dist/manifest-live.json \
  --key ~/.config/mote-updates/ed25519_seed.b64 \
  --notes-url https://dl.xiaotu.online/mote/release-notes-1.0.4.html \
  --out dist/manifest-live.json

# ④ 上传清单：方法同 ①，对象键改为 <product>/updates/stable/manifest.json，
#    Cache-Control: no-cache, max-age=60、Content-Type: application/json；随后复验
python3 tools/release/manifest_v2.py verify --manifest dist/manifest-live.json \
  --key ~/.config/mote-updates/ed25519_seed.b64
curl -fsSL "https://dl.xiaotu.online/mote/updates/stable/manifest.json?t=$(date +%s)" \
  | grep -o '"notes_url": *"[^"]*"'
```

- 小兔的两个发布脚本已把上述流程封装成一条命令：`NOTES_ONLY=true tools/package/publish_oss.sh`（或 `publish_windows.sh`，效果相同）。只上传 `docs/release-notes-<版本>.html` 并整体重签清单，不要求 dmg / 安装包 / `BUILD`；默认校验线上清单版本与 `VERSION` 一致，补历史版本用 `NOTES_VERSION=1.0.3`。
- `resign` 会拒绝未签名的清单，并自动刷新 `updated_at`；`--platform` 可只改一个平台段
- 换密钥后要用新密钥对应的 `--key`；重签结果必须能被客户端内置公钥验证通过才算完成

## 10. PowerShell 编码门禁（三仓库统一，2026-11-20 上线）

PowerShell 5 在 Windows 上只读 UTF-8 + BOM（`\xef\xbb\xbf`）的 `.ps1`；无 BOM 的 UTF-8 被当 GBK 读，中文字面量断裂 → 脚本崩溃（本次开发过程已多次触发）。三层防御：

| 层 | 位置 | 说明 |
|---|---|---|
| 检出时 | `.gitattributes`：`*.ps1 text eol=crlf working-tree-encoding=UTF-8` | git 层面的软约束（三仓库各一份） |
| 提交时 | `tools/hooks/pre-commit`（bash）+ `tools/hooks/setup-hooks.ps1`（UTF-8 + BOM 自验证） | 扫描所有 staged `.ps1`，前 3 字节不是 `EF BB BF` 直接阻断提交并给出修复命令 |
| 发布时 | `publish_windows.ps1`（三仓库） | 运行时兜底，编码异常主动报错 |

新机器首次 clone 后：

```powershell
cd <repo-root>
powershell -ExecutionPolicy Bypass -File tools\hooks\setup-hooks.ps1
```

之后 `git config core.hooksPath tools/hooks` 生效，每次 commit 自动检查，缺 BOM 直接 ExitCode 1 阻断并打印修复命令。**三个仓库各自独立**配置，互不影响。
