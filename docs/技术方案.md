# Mote 技术方案

> 本文描述 **当前（1.0.6）的实际架构**，并记录此前讨论过的架构改造方案 A/B（含备选 C）的取舍与最终选择。
> 写作口径：能从代码、构建脚本、验收记录直接核对的写成既成事实；来自设计稿或会话讨论、但尚未实机验证的明确标注。
> 关联文档：[阶段 A 设计稿](thin-shell-stage-a.md)、[阶段 B 设计稿](thin-shell-stage-b.md)、[阶段 A 验收记录](thin-shell-stage-a-acceptance.md)、[阶段 B 验收记录](thin-shell-stage-b-acceptance.md)、[复刻手册](REBUILD-GUIDE.md)。

## 1. 目标与约束

- **目标**：Markdown 查看/编辑器，正文的渲染与编辑交给系统 WebView，外壳保持薄，不引入 Electron/Tauri 一类运行时。
- **硬约束**：
  - 前端资源只有一份：`resources/web/`，两端构建共用。
  - 版本号只有一个来源：仓库根 `VERSION.txt`，构建时读取。
  - 平台能力（窗口、菜单、对话框、剪贴板、PDF、拖放）留在原生层，不依赖网页 API。
  - 不链接 Qt：macOS 用系统 WebKit/AppKit，Windows 用系统 WebView2/Win32。
- **非目标**：本文不重新论证产品功能，只记录架构与落地方式。

## 3. 分层职责

| 层 | 位置 | 职责 | 不做什么 |
|---|---|---|---|
| 前端 | [resources/web](../resources/web) | 块模型、渲染、编辑、查找替换、目录、主题、状态栏 | 不碰磁盘、不碰系统剪贴板（写入由外壳完成） |
| 核心 | [core](../core) | 协议、状态机、菜单表、图片落盘、分片切分、更新判定 | 不 include 任何平台头、不依赖图形库 |
| macOS 外壳 | [shell/mac](../shell/mac) | 窗口、菜单、对话框、WKWebView、PDF/HTML 导出、拖放、剪贴板、更新检查（交 Sparkle 安装） | 不重复实现消息分发 |
| Windows 外壳 | [shell/win](../shell/win) | 窗口、菜单、对话框、WebView2、拖放、剪贴板图片、PDF/HTML 导出、更新检查（WinHTTP） | 不重复实现消息分发 |
| 构建 | [native/CMakeLists.txt](../native/CMakeLists.txt) | 读版本号、按平台生成 target、拷贝前端/字体/示例 | 不成为第二份版本源 |

## 4. 关键协议与不变量

以下 5 条是迁移时明确保留的约束，代码里对应 `core/editor_controller.*` 与 `shell/*/web_host_view.*`：

1. **页面代次**：每次换页前自增，页面 URL 带 `#gN`；消息桥按 fragment 丢弃旧页迟到的消息。
2. **ready 前缓存**：正文、`<base>`、主题在页面 ready 前只记录，ready 后按顺序补发，避免相对图片按旧目录解析。
3. **临时页面 + `loadFileURL`**：页面模板写到文档目录的临时 HTML，再用文件 URL 加载，使相对资源可读；换目录必须重载页面。
4. **脏标记以最近保存文本为准**：标题 `name* - Mote` 只在正文与保存点不同时显示星号。
5. **复制/剪切由页面算内容、原生写剪贴板**：macOS 走 AppKit 响应链；Windows 走 `clipboardCopy` → 页面回传 `clipboardWrite` → 外壳写 `CF_UNICODETEXT` + `HTML Format`。

N3 额外补充：

- **大文档注入分三级**（仅 Windows）：JSON 字面量 ≤ 512 KB 走单条 `ExecuteScript`；≤ 1.5 MB 走 `PostWebMessageAsJson`；再大则按 `core/inject_chunks` 切片，逐片 `push` 到页面数组后一次拼接。
- **图片粘贴优先于文本**：`EditorHost::clipboardImage` 由平台解码为 PNG 字节，core 统一落盘并插入；平台返回 false 才回落到文本。
- **原生拖放**：只认 `CF_HDROP` 的文件路径，能否处理由 `EditorController::acceptsNativeFileDrop` 判定；`.md` 交给外壳走未保存确认，图片复制进 `assets/`。

## 5. 平台差异（实现事实）

| 能力 | macOS | Windows |
|---|---|---|
| 外壳 | AppKit，`NSApplication` + `NSWindow` | Win32，`wWinMain` + 自建消息循环 |
| WebView | WKWebView | WebView2（动态加载 `WebView2Loader.dll`） |
| 菜单 | `NSMenu`，由 `core/command_table` 生成 | `HMENU` + `HACCEL`，同一张表；`cmd`→`Ctrl` |
| 剪贴板 | AppKit `cut:/copy:/paste:` 响应链 | 页面桥；文本 + HTML + PNG/CF_DIB（WIC 转 PNG） |
| 拖放 | `NSDraggingDestination` | OLE `IDropTarget`（`shell/win/drop_target.*`） |
| PDF | CGPDFContext 分段抓取、A4 拼页 | `PrintToPdf` 分页导出 |
| HTML 导出 | 图片内联为 data URI | 图片内联为 data URI |
| 状态栏 | 页面内 `#statusbar`（`body.platform-mac`） | 页面内（`body.platform-win`） |
| 深色模式 | 跟随 `NSApp.effectiveAppearance` | 读注册表 `AppsUseLightTheme`，响应 `WM_SETTINGCHANGE` |
| 在线更新 | `manifest.json`（`platforms.macos`）+ Sparkle 2（清单 Ed25519 验签、替换、重启） | `manifest.json`（`platforms.windows`）+ WinHTTP，按安装形态下载 setup 或 portable |

**PDF 导出（macOS）**：导出前页面加 `body.pdf-export`（与 `@media print` 同一套清壳规则，不改 DOM），`pdfBegin()` 返回正文宽高与安全切点；外壳用 `createPDFWithConfiguration:` 按切点分段抓取，再逐页画进 595.28×841.89pt 的 A4 `CGPDFContext`。

- 切点：正文可在行间切；表格行、列表项、图片不可切；代码块高度不超过一页正文（约 1009 CSS px / 757pt）时按整块取切点，超出则退回行级切点，单独超高块整段缩放放进一页。表格仍按行切（样张里表格可在行间跨页，但不能劈开一行）。
- 版式对齐 Typora 样张：正文 10.33pt、页边距 37.6/45.4pt、正文宽 520.08pt；正文行距 15.73pt（样张 15.9pt，WKWebView 行盒按整像素取整后的最近值），表格单行行高 26.25pt（样张 26.2pt）。
- 每段 `createPDF` 只含本页内容再拼页，避免整段绘制指令重复导致体积膨胀。

## 6. 在线更新（0.3.6 起）

**选型：OSS 托管产物 + 自研检查 + 平台安装。**

- 不用纯 Sparkle 做检查：检查节奏、提示文案、渠道都要自己控；Sparkle 2 也没有公开「安装已下载包」的 API，所以自研只做策略（拉清单、比版本、弹提示），用户确认后调 `checkForUpdates:`，由 Sparkle 完成下载、验签、替换与重启，不重复下载 DMG。
- 清单统一为 Schema v2：两平台同一份 `manifest.json`，带 Ed25519 签名（`signature`），客户端只取本平台段；产物再按清单里的 SHA256 与字节数校验。版本判定先比 `version`，同版本再比 `build`（macOS 与 Windows 口径一致）；`rollout_percent` 已接入灰度分桶（install_id + build → 0–99 桶），`mandatory` 已接入强制更新（跳过灰度与「稍后」，只给「立即更新」），两端共用 `modules/update` 同一套判定。
- Sparkle 仍负责 macOS 的下载、appcast EdDSA 验签、替换与重启；自研模块只做清单检查与提示。

**清单契约**（`mote/updates/<channel>/`）：

- `manifest.json`：`manifest_version: 2`、`product`、`channel`、`signature`，以及 `platforms.macos` / `platforms.windows`。每段含 `version`、`build`（两端都由编译期 `MOTE_BUILD` 注入，发布号 = tag 序号）、`min_os`、`artifacts`——macOS 为 `dmg`，Windows 为 `setup` / `portable`，各带 `url`、`size`、`sha256`；可选 `notes_url`。
- Windows 只读 `platforms.windows`，不会把 `.dmg` 当成 Windows 包。
- `appcast.xml`：Sparkle 专用，enclosure 指向 `.dmg`，带 `sparkle:edSignature`。
- `notes_url` 是两端共用的可选字段：非空时「发现新版本」弹窗显示可点击的「查看完整更新说明…」；为空则不显示。2026-11-19 已为三款产品的在售版本补齐说明页，线上三份清单（mote 1.0.6、xiaotu 1.0.6、devcard 1.3.0）均含该字段；更早版本（如 1.0.0）生成于该字段上线前，客户端按空值处理，属预期行为。

**判定**（[modules/update/include/mote/update.h](../modules/update/include/mote/update.h)，两端共用）：

`parseUpdateManifest(text, platform, …)` → `compareVersions` → `decideUpdate`，输出 `Invalid / UpToDate / Available / UnsupportedSystem`。解析时按 `platform` 取 `platforms.macos` / `platforms.windows` 段；版本优先，同版本两端都比 build（本机 build 未知时跳过）。平台层只负责取清单、把判定翻译成提示，不复制判定逻辑。

**节奏与安装**：

| 项 | macOS | Windows |
|---|---|---|
| 首次检查 | 启动 10 秒后 | 启动 10 秒后 |
| 周期 | 24 小时 | 24 小时 |
| 手动入口 | Mote → 检查更新… | 文件 → 检查更新… |
| 弹窗内容 | 版本号、发布时间、包大小、可选「查看完整更新说明…」 | 同左，另加安装形态说明 |
| 下载进度 | Sparkle 自带窗口；构建缺 `Sparkle.framework` 时改为打开浏览器下载（提示手动安装） | TaskDialog 百分比进度条 + 已下载/总大小，可取消 |
| 失败重试 | 交给 Sparkle | 可重试错误自动重试 3 次、间隔 2 秒；4xx 与非法地址不重试 |
| 安装方式 | Sparkle 下载 DMG → EdDSA 验签 → 替换 bundle → 自动重启 | 两条路径先检查未保存文档；应用内下载（WinHTTP）→ SHA256 校验 → 安装版静默安装（`/VERYSILENT /RELAUNCH=1`）并重启；绿色版提示后自动退出并打开所在文件夹，由用户解压覆盖 |

Windows 的形态判定：exe 同级存在 `unins000.exe` 即为安装版，优先用 `artifacts.setup`；否则用 `artifacts.portable` 的 zip；清单缺首选产物时回落到另一种。

macOS 关闭 Sparkle 自带定时检查（`Info.plist` 的 `SUEnableAutomaticChecks=false`），检查权归自研模块；启动时把应用语言锁定为中文，避免 Sparkle 窗口随系统语言回退到英文。

**发布链路**：

- [tools/release/publish_macos.sh](../tools/release/publish_macos.sh)：公证门禁（`spctl` 必须为 Notarized Developer ID）→ `sign_update` 生成 appcast EdDSA → 更新 `appcast.xml` → 用 `manifest_v2.py` 生成/合并 `platforms.macos` 的 `manifest.json` → 上传 OSS → 线上校验版本、大小、SHA256 与签名。
- [tools/release/publish_windows.ps1](../tools/release/publish_windows.ps1)：校验 zip 内容（必需文件齐全、`Mote.exe` 版本与仓库根 `VERSION.txt` 一致、无 Qt 产物）→ 算 SHA256 → 用 `manifest_v2.py` 生成/合并 `platforms.windows`（`artifacts.setup` / `artifacts.portable`）→ 上传 zip、安装包与清单 → 线上校验。
- [tools/release/publish_windows.sh](../tools/release/publish_windows.sh)：`publish_windows.ps1` 的 macOS 端等价脚本，读同一份 `~/.config/xiaotu-updates/.env`，从 `dist/` 自动定位 zip 与 setup.exe，生成/合并 `platforms.windows` → 上传 zip、安装包、清单 → 线上校验；适合在 macOS 上直接发 Windows 包。
- 说明页默认自动携带：脚本检测到仓库里的 `docs/release-notes-<版本>.html` 就上传到 `mote/release-notes-<版本>.html` 并写入清单 `notes_url`；要指向外部页面时用可选环境变量 `NOTES_URL`（绝对地址）覆盖，此时不再上传本地文件。缺页则不写该字段，老清单与老客户端都不受影响。已发布版本可用 `manifest_v2.py resign --notes-url <地址>` 补发，无需重新打包。
- [tools/release/publish_site_oss.sh](../tools/release/publish_site_oss.sh)：把 `web/` 整站同步到独立桶 `xiaotu-site`（备案前的 `pre.xiaotu.online` 镜像），与安装包、清单所在的 `dl` 桶隔离；自动关闭公共访问阻断、写入 `SupportSubDir`、按类型设置缓存并做线上 9 个路径与 404 校验。
- [tools/release/deploy_site.sh](../tools/release/deploy_site.sh) 与 [packaging/nginx-xiaotu.conf](../packaging/nginx-xiaotu.conf)：备案后官网正式站发布到 ECS nginx，含 CSP、缓存、gzip 与 404。
- [packaging/renew_site_cert.sh](../packaging/renew_site_cert.sh)：`pre.xiaotu.online` 的 Let's Encrypt 证书续期（HTTP-01 挑战写入 OSS），续期后通过 OSS API 更新自定义域名证书。
- 一份清单两个平台段：`manifest.json` 同时承载 `platforms.macos` 与 `platforms.windows`，客户端只读本平台段，互不串用。

**已知边界**：

- 0.3.5 启动即崩，只能手动重装；自动更新从 0.3.6 起才有效。
- 当前双平台均为 1.0.6（Windows build 仍是旧编号 `202611191435`；自下个版本起 `build` = `v<semver>+<seq>` 的序号），统一走 v2 `manifest.json`；v1 清单退役前的升级已实测全绿（见 [发布工作流](发布工作流.md) 的升级记录）。
- 1.0.0 的线上清单生成于 `notes_url` 上线之前，没有该字段，弹窗不显示发布说明链接；新版本发布时说明页随包自动上传，无需手工补。
- 干净状态与带 quarantine 的首次安装已在 macOS 手工验证，但没有自动化覆盖；断网/下载中断仍未验证（Windows 对可重试错误会自动重试 3 次）。Windows 安装版与绿色版两条更新路径都会先检查未保存文档，确认干净后才下载；安装版下载后静默安装并自动重启，绿色版下载校验后提示并自动退出，同时打开所在目录，由用户解压覆盖。
- OSS 在中国香港，国内下载偏慢。备案完成后可把域名改指向国内桶（或加一层 CDN），`dl.xiaotu.online` 不变，客户端与清单中的绝对 URL 都无需改动。

## 7. 架构改造方案对比与选择

### 方案 A：Win32/C++ 薄外壳 + WebView2

- **做法**：新增 `shell/win/`，窗口/菜单/对话框/剪贴板用 Win32 与 COM 实现；协议、状态机、菜单表全部复用 `core/`；WebView2 只负责渲染。
- **收益**：与 macOS 结构对称；`Mote.exe` 约 1–2 MB + Loader，无 Qt DLL；core 可直接复用。
- **代价/风险**：Win32 细节要自己兜（IME、快捷键、TaskDialog 样式、拖放注册到 WebView2 子窗口）。

### 方案 B：Qt 外壳接 core

- **做法**：保留 Qt 窗口与打包，只把协议层替换为 `core/`，删掉重复的消息分发。
- **收益**：改动小、风险低，现有 Qt 构建链不动。
- **代价**：仍带 Qt DLL，包体维持 40 MB 量级；**不解决包体问题**，只是代码结构变干净。

### 备选 C：WPF/WinUI + WebView2

- **做法**：.NET 外壳，core 通过 C ABI 暴露。
- **代价**：需要 .NET 运行时或自包含数十 MB；跨语言边界与构建链更复杂。未采用。

### 选择与理由

**选 A**，理由按权重排序：

1. **目标驱动**：这次改造的核心指标是包体。B 不改变量级，C 引入新运行时，只有 A 把 macOS 的收益复制到 Windows。
2. **结构对称**：两端都是「薄外壳 + `core/` + 系统 WebView」，新增平台只补一层落地代码，不产生第二套状态机。
3. **复用已验证资产**：消息协议、图片落盘、脏标记、菜单表、诊断钩子都已在 macOS 上通过单测与验收，A 可直接消费。
4. **可回退**：Windows 原生外壳曾与 Qt 构建并存，验证不过可以继续用旧路径发布；N6 实机验收通过后，Qt 路径已于 2026-11-19 删除，现在的回退手段是发布上一版本。

方案 B 没有被否定为“坏方案”，而是被定位为**过渡对照**：迁移期如果 A 在实机上遇到短期无法解决的 Win32/WebView2 问题，可以先退回 B，完成 core 复用后再择机去 Qt。实际落地中 N6 验收通过后直接删除了 Qt 路径。

## 10. 风险、未验证项与回退

**在线更新：异常路径未覆盖**：

> 三产品已统一到 v2 `manifest.json` + 自研检查（Mote 1.0.6 已实测：启动后拉清单、验签、按 `version` 判定、Sparkle 弹窗/下载/原子替换），以下异常路径**尚未**有自动化覆盖，需在干净环境手工回归验证：

- 断网、下载中断、旧包残留等异常路径（两端都没有自动化覆盖）。
- 真实干净环境（新 Mac / 新用户账户、其它 macOS 版本）尚未覆盖；同一账户下隔离偏好与缓存、以及带 quarantine 的首次安装与升级已在 macOS 手工验证。
- Windows 安装版可直接覆盖安装；绿色包的解压覆盖仍是手动步骤（应用已自动退出并打开所在目录）。两者都不提供自动回滚到旧版本的能力。

**风险与回退**：

- Windows 原生外壳出问题：回退到上一发布版本（`shell/win/` 与 `core/` 都在仓库内，可随时重出包）。
- macOS 原生外壳出问题：同上，回退到上一发布版本；Qt 构建路径已在 2026-11-19 删除，不再作为回退手段。
- 更新装坏：清单与 appcast 可回滚到上一版本（同版本号不可复用，需发补丁版本）；Sparkle.framework 必须用 `ditto` 拷进 bundle 解开 symlink，否则 `codesign --deep` 报 `bundle format is ambiguous`。
- 分块注入失败：core 保留 pending，下次 ready 重试；平台层记录失败原因。
