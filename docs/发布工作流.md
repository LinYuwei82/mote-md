# 发布工作流

> 适用仓库：`xiaotu-inventory`（小兔进销存）、`dev_card_cpp`（DevCard）、`mote`（Mote）
> 配套文档：[OSS-发布布局](./OSS-发布布局.md)（每个对象键、大小、缓存头）

## 1. 总体结构

```
构建机（本地 / GitHub Actions）
   │  产出安装包 + 更新清单
   ▼
OSS 桶 xiaotu-update（cn-hongkong）→ 自定义域名 dl.xiaotu.online（CNAME 直连 OSS，无 CDN 层）
   │  安装包（immutable 1 年）+ 清单（60s）
   ▼
客户端启动 / 下载页 site.js 读取清单
```

三个产品共用同一套目录与缓存规则，只有「谁构建、谁上传」不同。

> `dl.xiaotu.online` 通过 OSS 的 CNAME 域名（`xiaotu-update.cn-hongkong.thepacificxxs.com`）
> 直接指向桶，**没有 CDN 层**：上传后源站立即生效，无需刷新缓存。响应里的
> `Cache-Control` 由 OSS 原样返回，只影响客户端侧缓存（清单 60s、安装包 1 年）。

## 2. 通用规则

| 项 | 约定 |
|---|---|
| 桶 / 区域 | `xiaotu-update` / `cn-hongkong` |
| 域名 | `https://dl.xiaotu.online` |
| 安装包 | `<product>/<v2 文件名>`（`<product>-<version>-<os>-<arch>-<type>.<ext>`），`public, max-age=31536000, immutable` |
| 更新清单 | `<product>/updates/<channel>/manifest.json`、`appcast.xml`，`no-cache, max-age=60`（v1 清单已退役删除，见 5 节） |
| 发布说明 | `<product>/release-notes-<版本>.html` |
| 手册 | `<product>/manual.pdf`（固定名，手工上传） |
| 版本 | **必须递增**（macOS 的唯一更新判据）；安装包同名覆盖无效，改包必须升版本（唯一例外：修复清单错误而同版本重发，见 4.1） |
| Windows 构建号 | 小兔 `XIAOTU_BUILD` / Mote `MOTE_BUILD` / DevCard `DEVCARD_BUILD`：三产品同口径。CMake configure 传值 → 编译进二进制 → 清单 `build` 必须**等于**编译值，客户端同版本时靠它判新。未注入时 DevCard `compiled_build_number()` 返回 0，自动回退到只比版本 |
| 通道 | `stable`（默认）/ `beta` |
| 凭据 | 按产品不同，见 2.1 |

### 2.1 凭据与签名私钥位置

| 产品 | OSS 凭据 | 更新签名私钥 |
|---|---|---|
| 小兔 | `~/.config/xiaotu-updates/.env`（AK/SK/桶名/区域，600；Windows 脚本兼容 `oss-credentials.env`） | `~/.config/xiaotu-updates/update_signing_2026.pem` |
| DevCard | `~/.config/devcard/release.env` | Sparkle（appcast）：`~/.config/devcard/sparkle-keys/private_key.pem`；清单 v2：`~/.config/devcard/manifest-keys/ed25519_seed.b64` |
| Mote | `~/.config/xiaotu-updates/.env`（可用 `OSS_ENV_FILE` 覆盖） | 清单：`~/.config/mote-updates/ed25519_seed.b64`（`SIGN_KEY`）；Sparkle：`~/.config/mote-updates/sparkle_ed25519_seed.b64`（`SPARKLE_KEY`）。两把独立密钥，不得混用 |

私钥只在 Mac 上；Windows 构建机通过 GitHub Secrets 接收签名材料（仅清单签名用）：
小兔 `XIAOTU_UPDATE_SIGNING_KEY`（Ed25519 私钥 PEM）、DevCard `DEVCARD_UPDATE_SIGNING_KEY`、
Mote `MOTE_UPDATE_SIGNING_KEY`（32 字节种子 base64）。

### 2.2 发布门禁 guard.py 与清单生成器 manifest_v2.py

三个仓库各有一份 `tools/release/guard.py` 和 `tools/release/manifest_v2.py`，内容完全一致
（CI 用同名 `.sha256` 校验，单仓库私改会失败）。

| 阶段 | 检查内容 |
|---|---|
| `preflight`（上传前） | 产品/通道合法、文件命名（v1 或 v2 规则）、版本单调、同名覆盖风险、dmg 内 `SUFeedURL`/版本/公钥、绿色包内清单地址；v2 额外校验 manifest.json 结构与 Ed25519 签名；**Windows BUILD_STR**：绿色包 zip 扫 `XXX_BUILD=<digits>` 静态字符串与 `--build` 参数比对，setup.exe 单独出现时用 innounp 解包后扫；zip+setup 共存时只扫 zip（同源于绿色包）；**DevCard 专属**：清单 `platforms.macos` + `platforms.windows` 必须同时存在、Windows `build` 必须等于 CMake 注入值 |
| `verify-live`（上传后） | 清单字段、大小、SHA256、下载 URL、Content-Type、appcast 版本、`edSignature` |
| `selftest` | 46 项离线用例（含 v2 schema 与 Ed25519 固定向量、DevCard 双平台强校验、BUILD_STR 正向匹配），CI 每次运行 |
| `manifest_v2.py selftest` | 26 项离线用例（RFC 8032 向量、generate→verify 全流程、macos 段 build 强制为 0 校验） |

v2 清单（`manifest.json`，schema 与命名见[更新清单Schema-v2](./更新清单Schema-v2.md)）
已上线，生成器与门禁用法：

```bash
# 生成并签名（--prev 合并另一平台段后整体重签）
tools/release/manifest_v2.py generate --product mote --platform windows \
    --version 1.0.4 --build 202611181542 --artifact portable=x.zip --key <私钥> \
    --prev dist/manifest.json --out dist/manifest.json
# 门禁：v2 命名 + 签名 + 与产物一致性
tools/release/guard.py preflight --product mote --kind win --file x.exe \
    --schema v2 --build 202611181542 --manifest dist/manifest.json --pub <公钥> --offline
```

修改任一文件后必须同步：

```bash
tools/release/sync_guard.sh      # 在 mote 仓库执行，同步两份并重写 .sha256
```

## 3. macOS 发布

一条命令完成：构建 → 签名 → 公证 → 校验包内 feed 地址 → 生成 `appcast.xml` / `manifest.json`（v2）→ 上传 → 线上复核。

Mote 的构建入口只有 `native/CMakeLists.txt`（AppKit + WKWebView，无 Qt）；
本地产物是 `dist/Mote-macOS-native-<版本>.zip` / `.dmg`，发布脚本上传时按 v2 规则
改名为 `mote-<版本>-macos-arm64.dmg`。

| 产品 | 版本来源 | 命令 |
|---|---|---|
| Mote | `VERSION.txt` | `tools/release/publish_macos.sh` |
| DevCard | `VERSION.txt` | `tools/release/publish_macos.sh` |
| 小兔 | `VERSION` | `tools/package/publish_oss.sh` |

> macOS 只认 `VERSION`：v2 清单的 `platforms.macos.build` 固定为 `0`，客户端（小兔 1.0.3 起）
> 的检查、待安装、验证期与恢复模式全部按版本号判定。只改 `XIAOTU_BUILD` / `MOTE_BUILD`
> 不会让 macOS 用户看到更新；构建号只写进 `Info.plist` 与 Sparkle appcast。

可选参数（三个产品接口不同）：

Mote 用环境变量开关：

```bash
bash packaging/package_macos.sh --dmg                     # 出 dist/Mote-macOS-native-1.0.4.dmg
SKIP_UPLOAD=true tools/release/publish_macos.sh           # 只本地生成清单，不碰 OSS
DMG_PATH=dist/Mote-macOS-native-1.0.4.dmg tools/release/publish_macos.sh  # 复用已有 dmg
```

DevCard 用命令行参数：

```bash
tools/release/publish_macos.sh --skip-build     # 复用已有 dmg
tools/release/publish_macos.sh --notes "说明"   # 写入 appcast 发布说明
tools/release/publish_macos.sh --dry-run        # 只出包与清单，不上传
```

小兔用环境变量开关：

```bash
OSS_SKIP=true tools/package/publish_oss.sh      # 只本地生成 + 验签，不碰 OSS
WARMUP=false tools/package/publish_oss.sh       # 关闭发布后的下载可达性验证
PRODUCT=xiaotu tools/package/publish_oss.sh     # 产品目录，默认且仅接受 xiaotu
```

## 4. Windows 发布

### 4.1 DevCard / Mote：走 GitHub Actions

1. 升版本并提交推送（只改仓库根 `VERSION.txt`）
2. Actions →「Windows 发布」→ Run workflow
   - 勾 `dry_run`：只构建、出包、跑门禁，不上传
   - 勾 `skip_setup`：只发绿色包，跳过 Inno 安装包
   - 都不勾：正式发布（绿色包 + 安装包 + 清单）
3. 完成后按第 6 节核对

需要配置的 Secrets：`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`。

本地发布时：`packaging/package_windows_native.ps1` 出绿色包，
`packaging/build_installer.ps1` 出 `dist/Mote-Setup-<版本>.exe`；
`publish_windows.ps1` 检测到安装包就一并上传，不存在则只发绿色包。

> **构建号必须与二进制里的值一致。** 客户端在版本相同时靠 `build`
> 判断有没有新构建；如果清单的 `build` 大于安装包里编译进去的值，用户每次检测都会
> 被提示同一版本，装完照旧，形成死循环（2026-11-19 mote 1.0.4 即因此重发）。
> 变量名：小兔 `XIAOTU_BUILD`、Mote `MOTE_BUILD`、DevCard `DEVCARD_BUILD`。
> DevCard 在 2026-11-19 补齐了 CMake 注入机制（`devcard_add_build_stamp()` →
> `-DDEVCARD_BUILD_STAMP=<UTC>`），与小兔 / Mote 对齐；未注入时回退到只比版本。
> Actions 里构建与发布是两个步骤、两个进程：构建步骤把实际生效的值经
> `<PRODUCT>_BUILD_STAMP` 传给发布步骤。本地发布时 `publish_windows.ps1` 优先用 `-Build`，
> DevCard 无 SkipBuild 时脚本自动触发 re-configure 确保 CMake 重新注入。

### 4.2 小兔：Windows 发布（两条路径）

私钥和 OSS 凭据留在 `~/.config/xiaotu-updates/`。2026-11-19 起 Windows 构建机可直接发布，
不需要拷回 Mac。

> 仓库里 GitHub Actions `release-windows.yml` 流程完整可用，
> 含 innounp 自动部署（打安装包后 → 下载 innounp-2 到 `~/.local-bin` → guard preflight 解包 setup.exe）。
> 小兔是私有仓库、Actions 消耗付费额度，当前额度不足时用下面的本地方案；额度恢复后直接改走 Actions。

**路径 A（推荐）：Windows 本机发布**

```powershell
cd D:\projects\xiaotu-inventory

# Windows 侧：构建
packaging\win\build-release.cmd 202611190003

# Windows 侧：发布（需要签名私钥，路径自动找 ~/.config/xiaotu-updates/update_signing_2026.pem）
powershell -ExecutionPolicy Bypass -File tools\package\publish_windows.ps1 `
  -Build 202611190003          # 不传也能自动从 CMakeCache 读
  -SkipUpload                  # dry-run：只生成 + 验签，不碰 OSS
  # 去掉 -SkipUpload 就是正式发布
```

`publish_windows.ps1` 自动：
1. 读仓库根 `VERSION` 拿版本号
2. 读 `build\windows\CMakeCache.txt` 拿 `XIAOTU_BUILD` 构建号（`-Build` 显式传入优先）
3. 找签名私钥（`-SignKeyPath` 显式传入 → `~/.config/xiaotu-updates/update_signing_2026.pem` → CI 环境变量 `XIAOTU_UPDATE_SIGNING_KEY`）
4. 调 `manifest_v2.py generate` 生成清单（取线上清单 `--prev` 合并另一平台段）
5. 调 guard.py `preflight`（v2 命名 + Ed25519 签名 + 绿色包内嵌地址 + **BUILD_STR 二进制二次校验**）
6. 凭据轮换自检（AccessKey 命中 git 受版本控制的文件即拒绝）
7. OSS 上传 → 线上 reachability 校验 → guard.py `verify-live`

> **BUILD_STR 机制**：2026-11-19 上线，CMake 加 `-DXIAOTU_BUILD_STR=<UTC>` 字符串宏，
> 壳 `updater_win.cpp` 放 `kBuildStamp` 静态字符串进二进制。guard.py preflight 从绿色包 zip
> 里扫出这个 build 号，与发布参数比对。不一致 → 阻断发布。
> setup.exe 单独存在时 guard.py 用 **innounp** 解包 ISCC 安装包后再扫。
> zip + setup 共存时只扫 zip（同源于绿色包）。

**路径 B（遗留）：Mac 发布**

把两个产物按相对路径拷回仓库（文件名不要改），然后：

```bash
cd /Users/lin/Projects/xiaotu-inventory
OSS_SKIP=true BUILD=202611180930 tools/package/publish_windows.sh   # 空跑
BUILD=202611180930 tools/package/publish_windows.sh                 # 正式上传
```

仓库里有 `docs/release-notes-<版本>.html` 时会自动一并上传，并把
`https://dl.xiaotu.online/xiaotu/release-notes-<版本>.html` 写进清单对应平台段的
`notes_url`；没有该文件则不写字段（客户端不显示「查看更新详情」）。

依赖已就绪：`~/.venvs/xiaotu-oss`（oss2 / cryptography / semver），桶名与区域会从 `.env` 自动读取。

## 5. 版本与清单约定

> v2 统一清单**已上线**（2026-11-18 三产品双平台全部切换，见
> [更新清单Schema-v2](./更新清单Schema-v2.md)。三个产品共用同一结构：
>
> | 文件 | 关键字段 |
> |---|---|
> | `manifest.json` | `manifest_version=2`、`product`、`channel`、`key_id`、`updated_at`、`platforms.<macos\|windows>.{version, build, min_os, artifacts.{dmg\|setup\|portable}.{url,size,sha256}}`、`signature`（Ed25519） |
> | `appcast.xml` | Sparkle 专用，不在 v2 范围，格式不变 |
>
> 客户端只取 `platforms.<自己的平台>`：更新判定 macOS 比 `version`，Windows 先比
> `version`、同版本再比 `build`；下载前验清单签名，下载后校验产物 SHA256。
> DevCard 2026-11-19 起 Windows 端同版本时也比 `build`（`compiled_build_number()`
> 返回 CMake 注入值，未注入回退 0 自动跳过），与小兔 / Mote 对齐；
> macOS 端所有产品（含 DevCard）同版本不比 `build`，只比版本号。
> DevCard 的 WebView 没有 Ed25519 能力，页面把清单原文交回本地服务端
> `POST /api/version/verify`（内嵌公钥）验签后再取 `artifacts`。
>
> v1 清单（`latest.json` / `windows.json`）已于 2026-11-18 升级实测全绿后删除，仅存档于 git 历史：
>
> | 文件 | 关键字段 |
> |---|---|
> | `latest.json` / `windows.json` | 各产品旧的扁平 / assets[] 结构 |

下载页版本号由 `site.js` 直接读 `manifest.json` 的 `platforms.*.artifacts.*`，**不需要改任何 HTML**。

## 6. 发布后核对（每次必做）

```bash
# 1) 清单
curl -s https://dl.xiaotu.online/<product>/updates/stable/manifest.json | python3 -m json.tool

# 2) 安装包可达且大小一致
curl -sI https://dl.xiaotu.online/<product>/<v2 文件名> | head -5

# 3) 包内地址（Windows 最容易被忽略的一步，以小兔绿色包为例）
curl -sL -o /tmp/p.zip https://dl.xiaotu.online/xiaotu/xiaotu-<v>-win64-portable.zip
python3 -c "import zipfile;z=zipfile.ZipFile('/tmp/p.zip');print(b'xiaotu/updates/stable/manifest.json' in \
z.read([n for n in z.namelist() if n.endswith('xiaotu-shell.exe')][0]))"

# 4) macOS dmg 内 SUFeedURL
curl -sL -o /tmp/p.dmg https://dl.xiaotu.online/<product>/<dmg>
hdiutil attach -nobrowse -readonly /tmp/p.dmg >/dev/null
/usr/libexec/PlistBuddy -c 'Print :SUFeedURL' -c 'Print :CFBundleVersion' \
  "/Volumes/<App>/<App>.app/Contents/Info.plist"
hdiutil detach "/Volumes/<App>" >/dev/null
```

判定标准：清单、安装包、**包内地址**三者一致；打开 `pre.xiaotu.online/download/`，1 分钟内版本号自动更新。
Windows 还要核对第 5 项：清单 `build` 与构建日志里的 `MOTE_BUILD` / `XIAOTU_BUILD` / `DEVCARD_BUILD` 逐位相同——不一致会表现为客户端反复提示同一版本（三产品同口径，2026-11-19 起 DevCard 也需核对）。

```bash
# 5) 构建号一致性（Windows）
curl -s https://dl.xiaotu.online/<product>/updates/stable/manifest.json \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['platforms']['windows']['build'])"
# 输出必须等于构建日志里的 MOTE_BUILD / XIAOTU_BUILD / 「构建号」
```

## 7. 常见拒绝原因

| 报错 | 原因 / 处理 |
|---|---|
| `版本回退` | 没升版本，或版本小于线上 |
| `目标已存在且大小不同` | 同版本重发，安装包不可覆盖，升版本 |
| `dmg 内 SUFeedURL 与发布地址不一致` | 产物是旧构建，重新构建，不要 `--skip-build` |
| `绿色包内嵌地址不是 .../updates/.../manifest.json` | 壳用了旧源码，重建壳 |
| `缺少 OSS_ACCESS_KEY_ID` | 凭据文件缺失或权限不是 600 |
| `清单 404` | 上传失败，或客户端/浏览器缓存了旧的 404（清单 60s 内可能仍命中缓存），稍后重试 |
| 客户端反复提示同一版本 | 清单 `build` 大于安装包内 `MOTE_BUILD` / `XIAOTU_BUILD` / `DEVCARD_BUILD`：重发同版本修复，或升版本发布；发布后按第 6 节第 5 项核对。三产品同口径（2026-11-19 起 DevCard 也适用） |
| `DevCard v2 清单 platforms 缺少 ['macos'/'windows']` | DevCard 当前阶段两平台同时发布，v2 manifest.json 必须同时含 `platforms.macos` + `platforms.windows`；发布脚本应从线上清单 `--prev` 合并后整体重签 |
| `未能确定编译时的 MOTE_BUILD` | `build-native-ninja/CMakeCache.txt` 里没有该变量（构建时未传 `-DMOTE_BUILD`），用 `-Build` 显式传入编译值 |

## 8. 历史版本清理

**当前策略（内测期）：桶内只保留每个产品的当前版本**，2026-11-19 已把全部历史包清零
（v1 命名 27 个 + v2 旧版本 9 个，共 116 MB）。发新版后如需清理上一版，按下面的白名单方式操作。

白名单取「三份 `manifest.json` + 三份 `appcast.xml` 里出现的所有地址」，只删除不在其中的
`<product>-<version>-<os>-<arch>-<type>.<ext>` 对象；**删除前必须校验零冲突**。

```bash
# 小兔仓库自带的按版本清理脚本（可选，默认保留 3 个 stable 版本）
tools/package/cleanup_oss_versions.sh --dry-run   # 先看计划
tools/package/cleanup_oss_versions.sh --force     # 真删
```

- 该脚本只识别小兔自己的命名，Mote / DevCard 需用上面的白名单方式手工清理
- 按「同一版本的 dmg / setup.exe / zip」整组删除
- `manifest.json`、`appcast.xml`、`manual.pdf`、`release-notes-*.html` 永不删除
- **风险**：删除后无法回滚，需要旧版本只能重新构建产物；删前确认清单/appcast 已指向新版本

## 9. 发布说明

- 文件命名与版本严格对应：`docs/release-notes-<版本>.html`；缺页时不写 `notes_url`，避免客户端出现死链
- 上传位置 `<product>/release-notes-<版本>.html`，`text/html; charset=utf-8`；缓存头统一为 `public, max-age=3600`
- 各产品发布脚本的现状：

| 产品 | 脚本 | 行为 |
|---|---|---|
| Mote | `tools/release/publish_windows.sh` / `.ps1` | 自动检测 `docs/release-notes-<版本>.html`，上传并写 `notes_url` |
| Mote | `tools/release/publish_macos.sh` | 2026-11-19 起同口径：自动检测并上传 `mote/release-notes-<版本>.html`、写入 `notes_url`；显式传 `NOTES_URL` 时以传入值为准，不再自动上传 |
| 小兔 | `tools/package/publish_windows.sh`（Windows）、`tools/package/publish_oss.sh`（macOS） | 同 Mote：自动检测并上传；也可用 `RELEASE_NOTES_FILE` 指定文件、`RELEASE_NOTES_URL` 指定外链 |
| DevCard | `tools/release/publish_macos.sh`、`tools/release/publish_windows.ps1` | 同 Mote：自动检测 `docs/release-notes-<版本>.html`，上传并写 `notes_url`；`DEVCARD_NOTES_URL` 可指定外链，`--notes` 文本另写进 macOS appcast |

- 显式传地址时必须是绝对 `http(s)`（Mote 与小兔脚本都会拒绝相对路径）；相对路径在客户端打不开
- 客户端展示：Windows 更新卡片在 `notes_url` 非空时显示「查看更新详情」，用系统默认浏览器打开（小兔 1.0.3 起）；macOS 由 Sparkle / 清单同字段提供链接
- 历史补页：`xiaotu/release-notes-1.0.3.html` 与 `mote/release-notes-1.0.4.html` 于 2026-11-19 补传，线上三份清单现均含该字段

### 9.1 给已发布版本补发 / 更换说明页

发布时漏了说明页（或要换成新的地址），不需要重新打包，按下面四步即可：

```bash
# ① 上传页面（与发布脚本同样的 Content-Type / Cache-Control）
set -a; . ~/.config/xiaotu-updates/.env; set +a
~/.venv-oss/bin/python - <<'PY'
import os, oss2
bkt = oss2.Bucket(oss2.Auth(os.environ["OSS_ACCESS_KEY_ID"], os.environ["OSS_ACCESS_KEY_SECRET"]),
                  f"https://oss-{os.environ['OSS_REGION']}.aliyuncs.com", os.environ["OSS_BUCKET"])
with open("docs/release-notes-1.0.4.html", "rb") as f:
    bkt.put_object("mote/release-notes-1.0.4.html", f,
        headers={"Cache-Control": "public, max-age=3600",
                 "Content-Type": "text/html; charset=utf-8"})
PY

# ② 取线上清单
curl -fsSL https://dl.xiaotu.online/mote/updates/stable/manifest.json -o dist/manifest-live.json

# ③ 只改 notes_url 并整体重签（其余字段与签名前的结构原样保留）
python3 tools/release/manifest_v2.py resign --manifest dist/manifest-live.json \
  --key ~/.config/mote-updates/ed25519_seed.b64 \
  --notes-url https://dl.xiaotu.online/mote/release-notes-1.0.4.html \
  --out dist/manifest-live.json

# ④ 上传清单：方法同 ①，对象键改为 <product>/updates/stable/manifest.json，
#    Cache-Control: no-cache, max-age=60、Content-Type: application/json；随后复验
python3 tools/release/manifest_v2.py verify --manifest dist/manifest-live.json \
  --key ~/.config/mote-updates/ed25519_seed.b64
curl -fsSL "https://dl.xiaotu.online/mote/updates/stable/manifest.json?t=$(date +%s)" \
  | grep -o '"notes_url": *"[^"]*"'
```

- 小兔的两个发布脚本已把上述流程封装成一条命令：`NOTES_ONLY=true tools/package/publish_oss.sh`（或 `publish_windows.sh`，效果相同）。只上传 `docs/release-notes-<版本>.html` 并整体重签清单，不要求 dmg / 安装包 / `BUILD`；默认校验线上清单版本与 `VERSION` 一致，补历史版本用 `NOTES_VERSION=1.0.3`。
- `resign` 会拒绝未签名的清单，并自动刷新 `updated_at`；`--platform` 可只改一个平台段
- 换密钥后要用新密钥对应的 `--key`；重签结果必须能被客户端内置公钥验证通过才算完成
- 三家密钥位置：Mote `~/.config/mote-updates/ed25519_seed.b64`、小兔 `~/.config/xiaotu-updates/update_signing_2026.pem`、DevCard `~/.config/devcard/manifest-keys/ed25519_seed.b64`
