# Mote 技术方案

> 本文描述 **阶段 B（Windows 原生外壳）验收之后、1.0.0 发布时的实际架构**，并记录此前讨论过的架构改造方案 A/B（含备选 C）的取舍与最终选择。
> 写作口径：能从代码、构建脚本、验收记录直接核对的写成既成事实；来自设计稿或会话讨论、但尚未实机验证的明确标注。
> 关联文档：[阶段 A 设计稿](thin-shell-stage-a.md)、[阶段 B 设计稿](thin-shell-stage-b.md)、[阶段 A 验收记录](thin-shell-stage-a-acceptance.md)、[阶段 B 验收记录](thin-shell-stage-b-acceptance.md)、[复刻手册](REBUILD-GUIDE.md)。

## 1. 目标与约束

- **目标**：Markdown 查看/编辑器，正文的渲染与编辑交给系统 WebView，外壳保持薄，不引入 Electron/Tauri 一类运行时。
- **硬约束**：
  - 前端资源只有一份：`resources/web/`，两端构建共用。
  - 版本号只有一个来源：`Mote.pro` 的 `VERSION`，构建时读取。
  - 平台能力（窗口、菜单、对话框、剪贴板、PDF、拖放）留在原生层，不依赖网页 API。
  - 迁移期间新旧构建共存，不打断已有发布链路。
- **非目标**：本文不重新论证产品功能，只记录架构与落地方式。

## 2. 当前架构总览

```
resources/web/                 editor.html / editor.css / editor.js（唯一前端，无框架、无构建）
        │  postMessage（window.webkit.messageHandlers.mote 兼容层）
        ▼
core/                          无 Qt、无平台 API，macOS 与 Windows 共用
  json / base64 / paths       协议解析、图片解码、路径与 file:// 目录
  js_bridge                   外壳 → 页面的全部脚本片段
  editor_controller           页面代次、ready 缓存、消息分发、脏标记、图片落盘
  image_store                 assets/ 落盘、重名与错误文案
  command_table               菜单唯一来源（4 组 33 个命令）
  inject_chunks               N3：按 JSON 转义预算切分大文档（UTF-8 安全）
  update                      更新清单解析、版本比较、升级判定（不碰网络与文件系统）
        │  EditorHost（虚接口：脚本、页面、剪贴板、对话框回调）
        ├──────────────────────────────┐
        ▼                              ▼
platform/mac/                   platform/win/
  AppKit + WKWebView              Win32 + WebView2
  NSMenu 由命令表生成             HMENU + HACCEL 由命令表生成
  CGPDFContext 分页导出           PrintToPdf 分页导出
  NSDraggingDestination           OLE IDropTarget
  AppKit 响应链处理剪贴板         页面桥 + CF_UNICODETEXT/HTML Format/PNG
  updater：latest.json            updater：WinHTTP 读 windows.json
  + Sparkle 下载/验签/替换        + 应用内下载 + SHA256 校验
                                 + 安装版静默安装（/RELAUNCH=1）
                                 + 绿色版退出并打开所在目录
        │                              │
        └────────── native/CMakeLists.txt ──────────┘
                macOS: Mote.app        Windows: Mote.exe
```

同时保留 **Qt 构建**（仓库根 `Mote.pro` + `src/`）作为共存与对照路径；正式发布已切到 `platform/mac/` 与 `platform/win/`，Qt 构建继续读取同一份 `resources/web/`，仅用于对照或回退。

## 3. 分层职责

| 层 | 位置 | 职责 | 不做什么 |
|---|---|---|---|
| 前端 | [resources/web](../resources/web) | 块模型、渲染、编辑、查找替换、目录、主题、状态栏 | 不碰磁盘、不碰系统剪贴板（写入由外壳完成） |
| 核心 | [core](../core) | 协议、状态机、菜单表、图片落盘、分片切分、更新判定 | 不 include 任何平台头、不依赖 Qt |
| macOS 外壳 | [platform/mac](../platform/mac) | 窗口、菜单、对话框、WKWebView、PDF/HTML 导出、拖放、剪贴板、更新检查（交 Sparkle 安装） | 不重复实现消息分发 |
| Windows 外壳 | [platform/win](../platform/win) | 窗口、菜单、对话框、WebView2、拖放、剪贴板图片、PDF/HTML 导出、更新检查（WinHTTP） | 不重复实现消息分发 |
| Qt 外壳（保留） | [src](../src) | 既有实现与对照路径 | 不新增功能，只维护兼容 |
| 构建 | [native/CMakeLists.txt](../native/CMakeLists.txt) | 读版本号、按平台生成 target、拷贝前端/字体/示例 | 不成为第二份版本源 |

## 4. 关键协议与不变量

以下 5 条是迁移时明确保留的约束，代码里对应 `core/editor_controller.*` 与 `platform/*/web_host_view.*`：

1. **页面代次**：每次换页前自增，页面 URL 带 `#gN`；消息桥按 fragment 丢弃旧页迟到的消息。
2. **ready 前缓存**：正文、`<base>`、主题在页面 ready 前只记录，ready 后按顺序补发，避免相对图片按旧目录解析。
3. **临时页面 + `loadFileURL`**：页面模板写到文档目录的临时 HTML，再用文件 URL 加载，使相对资源可读；换目录必须重载页面。
4. **脏标记以最近保存文本为准**：标题 `name* - Mote` 只在正文与保存点不同时显示星号。
5. **复制/剪切由页面算内容、原生写剪贴板**：macOS 走 AppKit 响应链；Windows 走 `clipboardCopy` → 页面回传 `clipboardWrite` → 外壳写 `CF_UNICODETEXT` + `HTML Format`。

N3 额外补充：

- **大文档注入分三级**（仅 Windows）：JSON 字面量 ≤ 512 KB 走单条 `ExecuteScript`；≤ 1.5 MB 走 `PostWebMessageAsJson`；再大则按 `core/inject_chunks` 切片，逐片 `push` 到页面数组后一次拼接。
- **图片粘贴优先于文本**：`EditorHost::clipboardImage` 由平台解码为 PNG 字节，core 统一落盘并插入；平台返回 false 才回落到文本。
- **原生拖放**：只认 `CF_HDROP` 的文件路径，能否处理由 `EditorController::acceptsNativeFileDrop` 判定；`.md` 交给外壳走未保存确认，图片复制进 `assets/`。

## 5. 平台差异（实现事实）

| 能力 | macOS | Windows（阶段 B） |
|---|---|---|
| 外壳 | AppKit，`NSApplication` + `NSWindow` | Win32，`wWinMain` + 自建消息循环 |
| WebView | WKWebView | WebView2（动态加载 `WebView2Loader.dll`） |
| 菜单 | `NSMenu`，由 `core/command_table` 生成 | `HMENU` + `HACCEL`，同一张表；`cmd`→`Ctrl` |
| 剪贴板 | AppKit `cut:/copy:/paste:` 响应链 | 页面桥；文本 + HTML + PNG/CF_DIB（WIC 转 PNG） |
| 拖放 | `NSDraggingDestination` | OLE `IDropTarget`（`platform/win/drop_target.*`） |
| PDF | CGPDFContext 分段抓取、A4 拼页 | `PrintToPdf` 分页导出 |
| HTML 导出 | 图片内联为 data URI | 图片内联为 data URI |
| 状态栏 | 页面内 `#statusbar`（`body.platform-mac`） | 页面内（`body.platform-win`） |
| 深色模式 | 跟随 `NSApp.effectiveAppearance` | 读注册表 `AppsUseLightTheme`，响应 `WM_SETTINGCHANGE` |
| 在线更新 | `latest.json` + Sparkle 2（EdDSA 验签、替换、重启） | `windows.json` + WinHTTP，按安装形态下载 exe 安装包或 zip 绿色包 |

## 6. 在线更新（0.3.6 起）

**选型：OSS 托管产物 + 自研检查 + 平台安装。**

- 不用纯 Sparkle 做检查：检查节奏、提示文案、渠道都要自己控；Sparkle 2 也没有公开「安装已下载包」的 API，所以自研只做策略（拉清单、比版本、弹提示），用户确认后调 `checkForUpdates:`，由 Sparkle 完成下载、验签、替换与重启，不重复下载 DMG。
- 不自建签名：Sparkle 2 强制 EdDSA（`SUPublicEDKey` + `sparkle:edSignature`），更新包完整性与来源已由它覆盖；因此不做 schema/api 版本、灰度分桶与强制更新。

**清单契约**（`mote/updates/<channel>/`）：

- `latest.json`：`version`、`url`、`size`、`sha256`、`min_os`、`published_at`，前两项必填；可选 `notes_url`。macOS 只读这份，指向 `.dmg`。
- `windows.json`：与 `latest.json` 同结构，`url` 指向绿色包 zip；可选 `setup_url` / `setup_size` / `setup_sha256` 指向安装包 exe，可选 `notes_url`。Windows 只读这份，避免把 `.dmg` 当成 Windows 安装包。
- `appcast.xml`：Sparkle 专用，enclosure 指向 `.dmg`，带 `sparkle:edSignature`。
- `notes_url` 是两端共用的可选字段：非空时「发现新版本」弹窗显示可点击的「查看完整更新说明…」；为空则不显示。1.0.0 的线上清单在该字段上线前生成，没有 `notes_url`，客户端按空值处理，属预期行为。

**判定**（[core/update.h](../core/update.h)，两端共用）：

`parseUpdateManifest` → `compareVersions` → `decideUpdate`，输出 `Invalid / UpToDate / Available / UnsupportedSystem`。平台层只负责取清单、把判定翻译成提示，不复制判定逻辑。

**节奏与安装**：

| 项 | macOS | Windows |
|---|---|---|
| 首次检查 | 启动 10 秒后 | 启动 10 秒后 |
| 周期 | 24 小时 | 24 小时 |
| 手动入口 | Mote → 检查更新… | 文件 → 检查更新… |
| 弹窗内容 | 版本号、发布时间、包大小、可选「查看完整更新说明…」 | 同左，另加安装形态说明 |
| 下载进度 | Sparkle 自带窗口 | TaskDialog 百分比进度条 + 已下载/总大小，可取消 |
| 失败重试 | 交给 Sparkle | 可重试错误自动重试 3 次、间隔 2 秒；4xx 与非法地址不重试 |
| 安装方式 | Sparkle 下载 DMG → EdDSA 验签 → 替换 bundle → 自动重启 | 两条路径先检查未保存文档；应用内下载（WinHTTP）→ SHA256 校验 → 安装版静默安装（`/VERYSILENT /RELAUNCH=1`）并重启；绿色版提示后自动退出并打开所在文件夹，由用户解压覆盖 |

Windows 的形态判定：exe 同级存在 `unins000.exe` 即为安装版，优先用 `setup_url`；否则用 `url` 的 zip；清单未提供 `setup_url` 时回落到 `url`，老清单仍可用。

macOS 关闭 Sparkle 自带定时检查（`Info.plist` 的 `SUEnableAutomaticChecks=false`），检查权归自研模块；启动时把应用语言锁定为中文，避免 Sparkle 窗口随系统语言回退到英文。

**发布链路**：

- [packaging/publish_macos.sh](../packaging/publish_macos.sh)：公证门禁（`spctl` 必须为 Notarized Developer ID）→ `sign_update` 生成 EdDSA → 更新 `appcast.xml` 与 `latest.json` → 上传 OSS → 线上校验版本、大小、SHA256 与签名。
- [packaging/publish_windows.ps1](../packaging/publish_windows.ps1)：校验 zip 内容（必需文件齐全、`Mote.exe` 版本与 `Mote.pro` 一致、无 Qt 产物）→ 算 SHA256 → 生成 `windows.json`（安装包存在时带 `setup_*`）→ 上传 zip、安装包与清单 → 线上校验 zip 与安装包的长度、清单里的版本、SHA256 与 `setup_url`。
- [packaging/publish_windows.sh](../packaging/publish_windows.sh)：`publish_windows.ps1` 的 macOS 端等价脚本，读同一份 `~/.config/xiaotu-updates/.env`，从 `dist/` 自动定位 zip 与 setup.exe，生成 `windows.json` → 上传 zip、安装包、清单 → 线上校验版本与 SHA256；适合在 macOS 上直接发 Windows 包。
- 各发布脚本都支持可选 `NOTES_URL` 环境变量：非空时写进清单的 `notes_url`，不设置则不写该字段，老清单与老客户端都不受影响。
- [packaging/publish_site.ps1](../packaging/publish_site.ps1)：下载页 `site/index.html` 上传到 OSS 桶根目录，上传前逐个 `HEAD` 校验链接、上传后比对线上内容。
- 两份清单分开存放：macOS 的 `latest.json` 与 Windows 的 `windows.json` 互不读取。

**已知边界**：

- 0.3.5 启动即崩，只能手动重装；自动更新从 0.3.6 起才有效。
- Windows 已发布 1.0.1（外壳修复包：浏览器快捷键开关、文件对话框内存泄漏、链接白名单、CRLF 保存、状态栏重放），macOS 仍为 1.0.0；`0.3.10 → 1.0.0` 的真实 Sparkle 升级路径（下载、验签、替换、重启）尚未冒烟验证，只有 0.3.7 → 0.3.8 的旧路径实测过。
- 1.0.0 的线上清单生成于 `notes_url` 上线之前，没有该字段，弹窗不显示发布说明链接；下次发版带 `NOTES_URL` 即自动生效。
- 干净状态与带 quarantine 的首次安装已在 macOS 手工验证，但没有自动化覆盖；断网/下载中断仍未验证（Windows 对可重试错误会自动重试 3 次）。Windows 安装版与绿色版两条更新路径都会先检查未保存文档，确认干净后才下载；安装版下载后静默安装并自动重启，绿色版下载校验后提示并自动退出，同时打开所在目录，由用户解压覆盖。
- OSS 在中国香港，国内下载偏慢。备案完成后只把 CDN 回源切到国内桶，`dl.xiaotu.online` 不变，客户端与清单中的绝对 URL 都无需改动。

## 7. 架构改造方案对比与选择

### 方案 A：Win32/C++ 薄外壳 + WebView2

- **做法**：新增 `platform/win/`，窗口/菜单/对话框/剪贴板用 Win32 与 COM 实现；协议、状态机、菜单表全部复用 `core/`；WebView2 只负责渲染。
- **收益**：与 macOS 结构对称；`Mote.exe` 约 1–2 MB + Loader，无 Qt DLL；core 可直接复用。
- **代价/风险**：Win32 细节要自己兜（IME、快捷键、TaskDialog 样式、拖放注册到 WebView2 子窗口）。

### 方案 B：Qt 外壳接 core

- **做法**：保留 Qt 窗口与打包，只把协议层替换为 `core/`，删掉重复的消息分发。
- **收益**：改动小、风险低，现有 Qt 构建链不动。
- **代价**：仍带 Qt DLL，包体维持 40 MB 量级；**不解决包体问题**，只是代码结构变干净。

### 备选 C：WPF/WinUI + WebView2

- **做法**：.NET 外壳，core 通过 C ABI 暴露。
- **代价**：需要 .NET 运行时或自包含数十 MB；跨语言边界与构建链更复杂。未采用。

### 选择与理由

**选 A**，理由按权重排序：

1. **目标驱动**：这次改造的核心指标是包体。B 不改变量级，C 引入新运行时，只有 A 把 macOS 的收益复制到 Windows。
2. **结构对称**：两端都是「薄外壳 + `core/` + 系统 WebView」，新增平台只补一层落地代码，不产生第二套状态机。
3. **复用已验证资产**：消息协议、图片落盘、脏标记、菜单表、诊断钩子都已在 macOS 上通过单测与验收，A 可直接消费。
4. **可回退**：`platform/win/` 独立于 Qt 构建，验证不过可以继续用 Qt 发布，不阻塞主分支。

B 没有被否定为“坏方案”，而是被定位为**过渡对照**：如果 A 在实机上遇到短期无法解决的 Win32/WebView2 问题，可以退回 B，先完成 core 复用，再择机去 Qt。

## 10. 风险、未验证项与回退

**在线更新尚未覆盖**：

- 断网、下载中断、旧包残留等异常路径（两端都没有自动化覆盖）。
- 真实干净环境（新 Mac / 新用户账户、其它 macOS 版本）尚未覆盖；同一账户下隔离偏好与缓存、以及带 quarantine 的首次安装与升级已在 macOS 手工验证。
- Windows 绿色包的解压覆盖是手动步骤（应用已自动退出并打开所在目录），没有安装器可以回滚。

**风险与回退**：

- Windows 原生外壳出问题：继续使用 Qt 构建发布，`platform/win/` 与 `core/` 留在仓库不影响发布。
- macOS 原生外壳出问题：Qt 构建仍可由 `Mote.pro` 产出。
- 更新装坏：清单与 appcast 可回滚到上一版本（同版本号不可复用，需发补丁版本）；Sparkle.framework 必须用 `ditto` 拷进 bundle 解开 symlink，否则 `codesign --deep` 报 `bundle format is ambiguous`。
- 分块注入失败：core 保留 pending，下次 ready 重试；平台层记录失败原因。

## 11. 事实来源
