# 发布工作流

> 适用仓库：`xiaotu-inventory`（小兔进销存）、`dev_card_cpp`（DevCard）、`mote`（Mote）
> 配套文档：[OSS-发布布局](./OSS-发布布局.md)（每个对象键、大小、缓存头）

## 1. 总体结构

```
构建机（本地 / GitHub Actions）
   │  产出安装包 + 更新清单
   ▼
OSS 桶 xiaotu-update（cn-hongkong）→ CDN dl.xiaotu.online
   │  安装包（immutable 1 年）+ 清单（60s）
   ▼
客户端启动 / 下载页 site.js 读取清单
```

三个产品共用同一套目录与缓存规则，只有「谁构建、谁上传」不同。

## 2. 通用规则

| 项 | 约定 |
|---|---|
| 桶 / 区域 | `xiaotu-update` / `cn-hongkong` |
| 域名 | `https://dl.xiaotu.online` |
| 安装包 | `<product>/<v2 文件名>`（`<product>-<version>-<os>-<arch>-<type>.<ext>`），`public, max-age=31536000, immutable` |
| 更新清单 | `<product>/updates/<channel>/manifest.json`、`appcast.xml`，`no-cache, max-age=60`（v1 遗留 `latest.json`/`windows.json` 不再更新，见 5 节） |
| 发布说明 | `<product>/release-notes-<版本>.html` |
| 手册 | `<product>/manual.pdf`（固定名，手工上传） |
| 版本 | **必须递增**；安装包同名覆盖无效，改包必须升版本 |
| 通道 | `stable`（默认）/ `beta` |
| 凭据 | 按产品不同，见 2.1 |

### 2.1 凭据与签名私钥位置

| 产品 | OSS 凭据 | 更新签名私钥 |
|---|---|---|
| 小兔 | `~/.config/xiaotu-updates/.env`（AK/SK/桶名/区域，600；Windows 脚本兼容 `oss-credentials.env`） | `~/.config/xiaotu-updates/update_signing_2026.pem` |
| DevCard | `~/.config/devcard/release.env` | Sparkle（appcast）：`~/.config/devcard/sparkle-keys/private_key.pem`；清单 v2：`~/.config/devcard/manifest-keys/ed25519_seed.b64` |
| Mote | `~/.config/xiaotu-updates/.env`（可用 `OSS_ENV_FILE` 覆盖） | 清单：`~/.config/mote-updates/ed25519_seed.b64`（`SIGN_KEY`）；Sparkle：`~/.config/mote-updates/sparkle_ed25519_seed.b64`（`SPARKLE_KEY`）。两把独立密钥，不得混用 |

私钥只在 Mac 上；Windows 构建机通过 GitHub Secrets 接收签名材料（仅清单签名用）：
小兔 `XIAOTU_UPDATE_SIGNING_KEY`（Ed25519 私钥 PEM）、DevCard `DEVCARD_UPDATE_SIGNING_KEY`、
Mote `MOTE_UPDATE_SIGNING_KEY`（32 字节种子 base64）。

### 2.2 发布门禁 guard.py 与清单生成器 manifest_v2.py

三个仓库各有一份 `tools/release/guard.py` 和 `tools/release/manifest_v2.py`，内容完全一致
（CI 用同名 `.sha256` 校验，单仓库私改会失败）。

| 阶段 | 检查内容 |
|---|---|
| `preflight`（上传前） | 产品/通道合法、文件命名（v1 或 v2 规则）、版本单调、同名覆盖风险、dmg 内 `SUFeedURL`/版本/公钥、绿色包内清单地址；v2 额外校验 manifest.json 结构与 Ed25519 签名 |
| `verify-live`（上传后） | 清单字段、大小、SHA256、下载 URL、Content-Type、appcast 版本、`edSignature` |
| `selftest` | 41 项离线用例（含 v2 schema 与 Ed25519 固定向量），CI 每次运行 |
| `manifest_v2.py selftest` | 18 项离线用例（RFC 8032 向量、generate→verify 全流程） |

v2 清单（`manifest.json`，schema 与命名见[更新清单Schema-v2](./更新清单Schema-v2.md)）
已上线，生成器与门禁用法：

```bash
# 生成并签名（--prev 合并另一平台段后整体重签）
tools/release/manifest_v2.py generate --product mote --platform windows \
    --version 1.0.3 --build 202611189999 --artifact portable=x.zip --key <私钥> \
    --prev dist/manifest.json --out dist/manifest.json
# 门禁：v2 命名 + 签名 + 与产物一致性
tools/release/guard.py preflight --product mote --kind win --file x.exe \
    --schema v2 --build 202611189999 --manifest dist/manifest.json --pub <公钥> --offline
```

修改任一文件后必须同步：

```bash
tools/release/sync_guard.sh      # 在 mote 仓库执行，同步两份并重写 .sha256
```

## 3. macOS 发布

一条命令完成：构建 → 签名 → 公证 → 校验包内 feed 地址 → 生成 `appcast.xml` / `manifest.json`（v2）→ 上传 → 线上复核。

| 产品 | 版本来源 | 命令 |
|---|---|---|
| Mote | `Mote.pro` 的 `VERSION` | `tools/release/publish_macos.sh` |
| DevCard | `VERSION.txt` | `tools/release/publish_macos.sh` |
| 小兔 | `VERSION` | `tools/package/publish_oss.sh` |

可选参数（三个产品接口不同）：

Mote 用环境变量开关：

```bash
SKIP_UPLOAD=true tools/release/publish_macos.sh           # 只本地生成清单，不碰 OSS
DMG_PATH=/path/to/Mote-macOS-native-1.0.2.dmg tools/release/publish_macos.sh  # 复用已有 dmg
```

DevCard 用命令行参数：

```bash
tools/release/publish_macos.sh --skip-build     # 复用已有 dmg
tools/release/publish_macos.sh --notes "说明"   # 写入 appcast 发布说明
tools/release/publish_macos.sh --dry-run        # 只出包与清单，不上传
```

小兔用环境变量开关：

```bash
OSS_SKIP=true tools/package/publish_oss.sh      # 只本地生成 + 验签，不碰 OSS
WARMUP=false tools/package/publish_oss.sh       # 关闭 CDN 预热
PRODUCT=xiaotu tools/package/publish_oss.sh     # 产品目录，默认且仅接受 xiaotu
```

## 4. Windows 发布

### 4.1 DevCard / Mote：走 GitHub Actions

1. 升版本并提交推送
2. Actions →「Windows 发布」→ Run workflow
   - 勾 `dry_run`：只构建、出包、跑门禁，不上传
   - 不勾：正式发布
3. 完成后按第 6 节核对

需要配置的 Secrets：`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`。

### 4.2 小兔：本地 Windows 构建 + Mac 发布

私钥和 OSS 凭据只留在 Mac，Windows 只负责编译打包。

> 仓库里已备好 `.github/workflows/release-windows.yml`（需要 Secrets：`OSS_ACCESS_KEY_ID`、
> `OSS_ACCESS_KEY_SECRET`、`XIAOTU_UPDATE_SIGNING_KEY`），流程与 DevCard / Mote 相同。
> 但小兔是私有仓库，Actions 消耗付费额度，当前额度不足会被 Billing 拦截，
> 因此现阶段采用下面的本地构建方案；额度恢复后可直接改走 Actions。

**Windows 侧**

```cmd
cd /d D:\projects\xiaotu-inventory
git pull
packaging\win\build-release.cmd 202611180930
```

- 构建号必须大于线上 `manifest.json` 中 `platforms.windows` 的 `build`
- 脚本自动：WebView2 SDK → 服务端 → 桌面壳（同一构建号）→ 自检壳内清单地址 → 绿色包 → 安装包
- 产物固定为：
  - `packaging\win\out\xiaotu-inventory-<版本>-win64-setup.exe`
  - `build\package\win\xiaotu-inventory-<版本>-win64.zip`

**Mac 侧**

把两个产物按上述相对路径拷回仓库（文件名不要改），然后：

```bash
cd /Users/lin/Projects/xiaotu-inventory
OSS_SKIP=true BUILD=202611180930 tools/package/publish_windows.sh   # 空跑：生成 + 验签
BUILD=202611180930 tools/package/publish_windows.sh                 # 正式上传
```

依赖已就绪：`~/.venvs/xiaotu-oss`（oss2 / cryptography / semver），桶名与区域会从 `.env` 自动读取。

## 5. 版本与清单约定

> v2 统一清单**已上线**（2026-11-18 三产品双平台全部切换，见
> [更新清单Schema-v2](./更新清单Schema-v2.md)。三个产品共用同一结构：
>
> | 文件 | 关键字段 |
> |---|---|
> | `manifest.json` | `manifest_version=2`、`product`、`channel`、`key_id`、`updated_at`、`platforms.<macos\|windows>.{version, build, min_os, artifacts.{dmg\|setup\|portable}.{url,size,sha256}}`、`signature`（Ed25519） |
> | `appcast.xml` | Sparkle 专用，不在 v2 范围，格式不变 |
>
> 客户端只取 `platforms.<自己的平台>`：更新判定 macOS 比 `version`，Windows 先比
> `version`、同版本再比 `build`；下载前验清单签名，下载后校验产物 SHA256。
>
> v1 遗留（旧内测客户端退役前不删除，新发布不再写入）：
>
> | 文件 | 关键字段 |
> |---|---|
> | `latest.json` / `windows.json` | 各产品旧的扁平 / assets[] 结构 |

下载页版本号由 `site.js` 直接读 `manifest.json` 的 `platforms.*.artifacts.*`，**不需要改任何 HTML**。

## 6. 发布后核对（每次必做）

```bash
# 1) 清单
curl -s https://dl.xiaotu.online/<product>/updates/stable/manifest.json | python3 -m json.tool

# 2) 安装包可达且大小一致
curl -sI https://dl.xiaotu.online/<product>/<v2 文件名> | head -5

# 3) 包内地址（Windows 最容易被忽略的一步，以小兔绿色包为例）
curl -sL -o /tmp/p.zip https://dl.xiaotu.online/xiaotu/xiaotu-<v>-win64-portable.zip
python3 -c "import zipfile;z=zipfile.ZipFile('/tmp/p.zip');print(b'xiaotu/updates/stable/manifest.json' in \
z.read([n for n in z.namelist() if n.endswith('xiaotu-shell.exe')][0]))"

# 4) macOS dmg 内 SUFeedURL
curl -sL -o /tmp/p.dmg https://dl.xiaotu.online/<product>/<dmg>
hdiutil attach -nobrowse -readonly /tmp/p.dmg >/dev/null
/usr/libexec/PlistBuddy -c 'Print :SUFeedURL' -c 'Print :CFBundleVersion' \
  "/Volumes/<App>/<App>.app/Contents/Info.plist"
hdiutil detach "/Volumes/<App>" >/dev/null
```

判定标准：清单、安装包、**包内地址**三者一致；打开 `pre.xiaotu.online/download/`，1 分钟内版本号自动更新。

## 7. 常见拒绝原因

| 报错 | 原因 / 处理 |
|---|---|
| `版本回退` | 没升版本，或版本小于线上 |
| `目标已存在且大小不同` | 同版本重发，安装包不可覆盖，升版本 |
| `dmg 内 SUFeedURL 与发布地址不一致` | 产物是旧构建，重新构建，不要 `--skip-build` |
| `绿色包内嵌地址不是 .../updates/.../manifest.json` | 壳用了旧源码，重建壳 |
| `缺少 OSS_ACCESS_KEY_ID` | 凭据文件缺失或权限不是 600 |
| `清单 404` | 上传失败或 CDN 缓存，60s 后重试 |

## 8. 历史版本清理

仅小兔仓库带该脚本：

```bash
tools/package/cleanup_oss_versions.sh --dry-run   # 先看计划
tools/package/cleanup_oss_versions.sh --force     # 真删
```

- 默认保留最近 3 个 stable 版本，至少保留 1 个
- 按「同一版本的 dmg / setup.exe / zip」整组删除
- **风险**：若 macOS 清单仍指向旧版本，整组删除会打断 Mac 下载。此时应先升 macOS，或只删该版本的 Windows 两个文件
- `manifest.json`、`latest.json`、`appcast.xml`、`windows.json`、`manual.pdf`、`release-notes-*.html` 永不删除

## 9. 发布说明

- 文件命名与版本严格对应：`release-notes-<版本>.html`
- Mote 的 Windows 发布会自动上传仓库根部的 `docs/release-notes-<版本>.html`
- DevCard / 小兔需手工上传，上传后务必访问一次确认 200
- 小兔可用 `RELEASE_NOTES_URL=https://...` 把说明地址写进清单（文件仍需先自行上传）
